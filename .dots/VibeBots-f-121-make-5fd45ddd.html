F-121 Resync elevator conflicts with authoritative state

Require expected depth plus an idempotency key, distinguish elevator rejection reasons, and replace the stale client view from one typed authoritative snapshot. Stage and validate world, active slot, gear, full inventory, balance, checkpoint, and rail state before deleting or mutating local state, then commit them once to the pinned slot. Parse each accepted or authoritative-reject elevator body through one strict, bounded current-version schema before alerts, local writes, or persistence. Require every gear and consumable key, reject unknown or extra keys, require nonnegative integers within shared sim and database bounds, and require equality between duplicated elevator, elevatorColumn, ladder, and plank fields and their nested values. Never fall back to local gear, bought stock, defaults, or rail-only response fields. Any omission, unknown or extra key, mismatch, partial validity, legacy shape, active-slot drift, or movement away from the pinned surface snapshot performs zero local mutation and enters blocked reconciliation. A malformed world or gear HTTP 200 must fail without adopting defaults. A malformed mutation HTTP 200, status-null transport loss, generic 503, or other ambiguous response is an unknown commit outcome: block blind retry, reconcile first, and keep a persistent recovery surface with Retry plus Start fresh until authority is restored. Clear account-trip state only with a validated cleared true body and a revision or fingerprint compare-and-delete whose affected-row result proves an older cleanup did not erase a newer PUT. Cover active-slot drift, in-flight movement away from the surface snapshot, world success plus gear failure, every malformed 200 boundary, empty and partial inventory objects, unknown and extra keys, numeric bounds, duplicated-field mismatch, only one valid inventory object, cleared false, a newer PUT racing DELETE, lost-success transport, generic 503 after commit, full inventory replacement on accepted and rejected paths, zero mutation or persistence on invalid input, persistence across reload, and controls staying blocked until recovery. Preserve one success-only elevator.upgrade balance event per committed purchase. Persist and deduplicate one bounded structured outcome per place, extend, or temporary legacy relocation request through a transactional outbox or equivalent durable record, including retry and crash recovery, while telemetry delivery failures never fail committed gameplay. Log expected preflight cash-out races with the stable trip conflict code at warning severity, not as generic persistence errors. Scrub exact shaft coordinates, full submitted gear objects, and coordinate-bearing detail strings from every upgrade and cash-out telemetry path, using bounded server-derived placement states and explicit absence assertions. For request validation failures, retain only bounded value kinds, issue codes and paths, presence flags, and bucketed counts. Never retain rejected numeric values. For gear ownership failures, omit the submitted gear digest entirely, keep player-facing copy separate from telemetry, and emit a stable reason with a bounded gear track when relevant plus a structured placement state for rail mismatches. Serialized route tests must assert the raw monitoring line contains no rejected values, submitted gear object, shaft coordinate, or coordinate-bearing detail. Retry reconciliation itself must be single-flight at the store boundary. Capture the pinned slot once, keep one shared in-flight promise, return that same promise and result to every concurrent caller, run exactly one destructive resync chain, clear the guard in finally, and allow a later retry only after settlement. Use a deferred concurrency test to prove concurrent direct action callers produce one world read, one gear read, one checkpoint cleanup, identical results and final recovery state, while a later retry starts a fresh sequence. The required expectedDepth guard is valid partial safety, but its missing-field response must give the affected cached client visible reload or update guidance rather than the internal text expectedDepth is required. Pin the exact player-facing response in the route test. Keep Q-027 honest: do not name a telemetry-based revisit criterion unless one real bounded reason-only signal exists for the reject. Never add raw request values or shaft coordinates to create that signal. The depth guard does not protect a lost-success retry of the free legacy relocation because relocation changes its marker and column but leaves depth unchanged. An identical retry can pass expectedDepth and column checks, fall through to paid extend, charge, and advance a rail. Require a request id plus validated bounded operation intent. Durable dedup must replay the original authoritative relocation result, never extend or charge, never emit a second balance or mutation-outcome event, and resync authority. Cover the accepted relocation followed by an identical lost-response retry as a sequential route regression. Rail conflict recovery must become fail-closed before any asynchronous reconciliation. Capture activeSlot once at conflict entry, set both the in-memory railResyncFailed gate and that pinned slot's durable marker before awaiting resync, and never re-read activeSlot when clearing or retaining the marker. A deferred buy test must hold the first conflict world read open, issue both buyElevator() and buyElevator(column), and prove later callers emit no second upgrade request or destructive resync while the first chain is pending. Hydration must detect any persisted blocked slot before active-slot authority is known. A cold offline store that defaults to slot 1 while slot 2 or 3 is marked must stay blocked, expose Retry plus Start fresh, and never rely on expectedDepth because equal-depth slots can still have different columns, gear, checkpoint, or world. Cover a slot 2 or 3 marker without a trip, active-slot drift during resync, the original marker retained on failure, and the pinned marker cleared only by complete typed authority.
