CI Workflow

This document records the VibeBots CI policy for fast parallel development without reducing the release bar.

Principles

  • Cancel superseded work. A newer push to the same branch or pull request cancels older CI for that ref.
  • Run independent gates in parallel. Dash, purity, whitespace, lint, type-check, unit tests, build, and smoke should not wait behind each other unless they depend on the same artifact.
  • Keep every push covered by a small critical smoke set.
  • Run the full Playwright smoke matrix on a schedule and by manual dispatch, and run it locally when a risky slice touches broad UI behavior.
  • Track the latest remote tip. If a pushed commit is included in a newer origin/main tip, stop waiting on superseded runs and verify the current tip instead.

Required Push Gates

For pushes to main and pull requests, the required gate is the parallel CI set:

  • quality: dash check, sim purity, whitespace check, and Biome lint.
  • typecheck: Next route type generation and TypeScript.
  • unit: Vitest unit and route tests, followed by the deterministic golden suite.
  • build: production Next build.
  • e2e-critical: sharded Playwright smoke over the critical routes.

The critical smoke set lives in package.json as pnpm test:e2e:critical. It covers account sign-in entry, latest release notes, save-slot load refresh, and the deterministic mine dig loop. Render-dependent bunker-claim entry, fatal-fall, and mine-motion assertions remain in the render tier instead of the required software-rendered gate.

E2E shards use Playwright's test-level sharding with ONE worker per shard, for both Critical and Full E2E. The parallelism comes from separate shard jobs, never workers inside a runner, because the software-rendered suite is CPU-bound: two workers on the 4-vCPU runner make each SwiftShader render compete for CPU and starve rendering-dependent tests into multi-minute timeouts (a two-worker Full E2E dispatch failed ~60 tests, including specs that pass at one worker in the required Critical gate). The Full E2E matrix instead uses many shards (see Full Smoke below) so each shard is small enough to finish at one worker inside the budget.

Full Smoke

The full Playwright smoke suite still exists as pnpm test:e2e. CI runs it in thirty-two shards, one worker each, 35-minute budget, for nightly scheduled runs and manual workflow_dispatch runs with full_e2e enabled. Sizing history: the original 4 shards / 1 worker / 20 minutes carried ~52 tests per shard at ~2 minutes apiece and completed only ~8 before the budget expired, timing out and cascading to red for a week; 8 shards / 2 workers / 30 minutes finished inside budget but the two-worker CPU contention starved ~60 rendering-dependent tests into timeouts; 16 shards / 1 worker / 35 minutes removed the contention (unique failures fell to ~30, all shards 6 to 15 minutes) but two shards holding clusters of slow software-rendered specs ran long; thirty-two shards of ~6 tests keep even a slow-cluster shard well inside the budget. Parallelism scales by shards, never workers or a bigger per-test cap, when the software renderer is the bottleneck. F-131 made the timeout visible; F-132 owns the deeper renderer-speed work.

Local pnpm test:e2e uses two file-level workers by default. Route-owned specs such as arena, workshop, routes, and API smoke can run beside focused mine feature specs such as core, bunker, viewport, save-slot, surface navigation, UI, and transport coverage. Keep canvas-heavy mine tests file-owned and avoid test-level mine concurrency unless intentionally stress-testing with PLAYWRIGHT_WORKERS=<n>.

Run the full suite locally or through manual dispatch before merging work that changes shared UI shell behavior, cross-route storage state, release-note infrastructure, Playwright harness behavior, or other broad surfaces where the critical set is too narrow.

Internal deadline and evidence (F-131). Each Full E2E shard has a 35-minute GitHub job budget. Before the tests run, the job computes a Playwright globalTimeout from the budget still left after checkout, install, and build, reserving 150 seconds for teardown, the HTML/JSON report, and the artifact upload, and injects it as E2E_GLOBAL_TIMEOUT_MS (parsed by src/lib/playwright-global-timeout.ts). A slow or hung shard therefore STOPS itself as a normal Playwright failure with a written report instead of being cancelled at the job deadline with zero artifacts. The upload step (if: failure()) then runs and retains playwright-report/ (HTML plus results.json) and test-results/ (traces and screenshots). This deadline is unset for local runs and Critical E2E, which run unbounded. To prove the path, dispatch the workflow with a low full_e2e_global_timeout_ms (for example 30000): every shard times out fast and the run concludes failure with artifacts, not cancelled. What that low-value proof shows is exactly the failure-not-cancel plus upload-runs mechanism; the retained artifact is playwright-report/ (HTML plus results.json) and one error-context.md, because a 30-second budget expires during startup before any test runs. Per-test evidence depends on tests actually running: a test that FAILS before the deadline captures a screenshot (screenshot: only-on-failure, taken on the first attempt) and, on its retry, a trace (trace: on-first-retry); a test still mid-run when the hard whole-suite deadline interrupts it may have neither, which is an inherent limit of a hard stop, not something a trace mode can guarantee. The precise evidence guarantee is therefore narrower than "always has traces": the run always fails red (never cancels), the if: failure() upload always runs, and it is never empty (a pre-upload step writes a NO-REPORT.txt marker if the HTML report is somehow absent), so a timed-out matrix always leaves a named, downloadable signal to triage, plus per-test screenshots and traces for whatever failed before the deadline.

Stable Case Inventory

Every Playwright case carries exactly one stable case-id annotation and exactly one capability tag: @functional, @render, @visual, or @soak. Titles, filenames, and line numbers remain descriptive context only. They do not control CI routing.

pnpm ci:inventory discovers the live Playwright suite and validates missing or duplicate IDs, missing or multiple capabilities, unknown tags, pixel assertions inside @functional, @critical outside @functional, stale quarantine entries, quarantine capability drift, and expired or overlong quarantine deadlines. The command has no hardcoded test count. Its count comes from Playwright discovery, so adding or removing a case changes the inventory instead of bypassing it.

The Stage 0 baseline contains 200 cases: 129 functional, 61 render, 3 visual, and 7 soak. CI uploads the generated inventory with discovery timing. Browser jobs also emit one bounded timing record per case attempt so later duration-based sharding uses measured stable identities.

The required Critical E2E command selects @critical and @functional together. Its four Stage 0 cases are E2E-ACCOUNT-0001, E2E-MINE-CORE-0002, E2E-MINE-SAVE-SLOTS-0002, and E2E-RELEASE-NOTIFICATIONS-0001. Pixel, renderer, and elapsed-frame assertions cannot enter the required subset through a title edit.

Deterministic Goldens

pnpm test:goldens runs versioned, browser-independent combat, mining, economy, replay, and world-snapshot vectors from tests/goldens/vectors. Every vector has a stable ID, seed, step count, action log, complete gear or design inputs where applicable, SIM_VERSION, MINE_VERSION for mine rules, a final FNV-1a snapshot hash, and selected semantic outcomes. A mismatch reports the vector inputs plus field paths and old and new values.

Golden output is updated only with pnpm test:goldens:update -- --reason <text>. The updater refuses an empty reason and refuses changed output while the relevant version constant is unchanged. Accepted updates append a machine-readable entry to tests/goldens/change-manifest.json, and each changed vector links to that entry. Tests reject a vector whose expected hash, semantic outcomes, changed-field list, prior result, or version no longer continues the manifest history, including a hand-edited baseline whose manifest version does not advance. A relevant version bump with no covered output change emits a review warning so unnecessary bumps or missing coverage stay visible.

The required golden job runs on Ubuntu 24.04 with Node.js 22.22.1. Exact hashes and floating-point comparisons are authoritative only in that pinned CI environment; changing either pin is a reviewed baseline event.

Scheduled Run Visibility (F-047)

A red nightly full-matrix run must be visible to the next agent without anyone listing workflow runs by hand. Rule 5 step 3 in AGENTS.md makes the check part of every slice start. Filter by --event schedule on the server rather than a client-side select over the default page: scheduled runs are rare, so a day of push and PR runs pushes the newest schedule run past the default 20-run page and a select(.event == "schedule") pipe then returns null (an empty result reads as "no red", the exact failure this gate exists to prevent). Also filter --status completed, so a queued or still-running schedule run (null conclusion) cannot mask an older completed red one:

gh run list --workflow CI --event schedule --status completed --limit 1 \
  --json conclusion,createdAt,databaseId,headSha

If the newest completed scheduled conclusion is failure and less than a day old, triage before picking a slice: inspect the failed jobs (gh run view <id> --log-failed), and if any failure is outside the known-flake list below, the regression IS the next slice. A known-flake-only red gets one line in the current slice's progress entry naming the run id, so the rot is on the record.

Timeout cancellations are red (F-131). A scheduled run whose conclusion is cancelled is red and must be triaged the same way. Evaluate the conclusion after fetching the newest completed schedule run; do not try to fold the conclusion into the list filter, because a matrix where some shards failure and others cancelled still rolls up as one run you must inspect. Supersession here is Full-E2E-specific, ancestry-based, and stricter than the push-run closeout rule: a push or PR run on a newer main SHA does NOT supersede a scheduled timeout, because push and PR gates never run the Full E2E matrix, so a newer green push proves nothing about Full E2E. A red scheduled run is superseded only by a later run that actually COMPLETED the Full E2E matrix (a newer scheduled run or a full_e2e manual dispatch) on a commit that CONTAINS the red commit as an ancestor (git merge-base --is-ancestor <red-sha> <newer-sha>), not merely a chronologically or numerically newer SHA. Until such a completed matrix exists and is green, a non-superseded cancelled or failure conclusion on the newest completed schedule run stands and must be triaged.

Known Full E2E flakes (fail intermittently on unmodified main; do not chase inside unrelated slices, but a slice may claim one deliberately): the holodeck pinch-zoom spec (holodeck.spec.ts REQ-021 camera test), the bunker claim-edit spec (mine-bunker.spec.ts "claims can be edited before banking"), the falling-rock camera spec, the raid-XP overlap retry spec (mine-bunker.spec.ts, a fix branch exists), the account-sync conflict-choice spec (mine-account-sync.spec.ts), and the first-person bunker specs under software rendering (mine-bunker-fp.spec.ts "performance telemetry attributes samples to the active surface (F-100)" and "first-person bunker viewer walks, looks, jumps, and exits in place"), triaged 2026-07-20 from scheduled run 29734723001: both pass locally in about 30s each but run 1.3 to 1.9 minutes under the CI software renderer and can miss their WebGPU-fallback pixel and telemetry assertions, and their retries help push the shard past its budget into a timeout cascade (the broader stabilization is F-132). Update this list when a flake is fixed or a new one is triaged.

Resizing history and the contention finding (2026-07-21): the first resize to 8 shards / 2 workers / 30 minutes fixed the timeout cascade (dispatch 29885827771 completed every shard in 3 to 28 minutes), but completing revealed the two-worker cost. A comprehensive scan of that run and its follow-up (dispatch 29889999826, which added the software-fallback DPR cap) showed ~68 then ~59 unique tests failing, dominated by mine, elevator, viewport, and fp specs, almost entirely with multi-minute timeouts (for example "Test timeout of 240000ms exceeded" on tests that finish in ~30s locally and at one worker in the Critical gate). That is CPU starvation from two SwiftShader renders sharing 4 vCPUs, not per-test flakiness. The fix reverted to one worker and doubled the shards to sixteen so each stays small enough to fit the 35-minute budget without contention. The software-fallback DPR cap (FallbackDprCap) stays, since faster frames help the one-worker path too. The residual after that is the genuine software-rendering flakes (holodeck pinch-zoom, account-sync conflict, a couple of fp pixel/telemetry specs), which remain F-132's deeper renderer-speed work.

Agent Behavior

  • After a direct push to main, fetch origin/main and verify the pushed commit is still in the current remote history.
  • If the remote tip advances and still contains the pushed commit, follow the newest remote tip's checks, not the older superseded run.
  • If a newer remote tip does not contain the pushed commit, stop and reconcile before claiming the work shipped.
  • Do not wait on cancelled, superseded, or older in-progress runs once a newer verified remote tip contains the commit being closed out.
  • Do not point the standard Playwright suite at protected production Vercel URLs with PLAYWRIGHT_BASE_URL. Use local or CI Playwright for app behavior, and use GitHub deployment status plus Vercel metadata for production deploy readiness.

Visual Regression Baselines

The full smoke suite includes tests/e2e/visual-baselines.spec.ts: paused Block Gallery scenes (terrain and classic ores), clipped to the block rows and screenshotted against committed per-platform baselines with toHaveScreenshot (maxDiffPixelRatio 0.02). The clip excludes the miner: its time-driven emissives (chest screen, visor, beacon) never pixel-stabilize, which fails Playwright's stable-capture check. The tests skip when the running platform has no committed baselines, so they never block a suite on a fresh platform.

Bootstrap or refresh: dispatch the CI workflow with update_visual_baselines=true. The dedicated job rebuilds, regenerates the snapshots with UPDATE_VISUAL_BASELINES=1 and --update-snapshots (the env opt-in exists because Playwright's default missing-snapshot policy silently writes and passes, which would make an uncommitted suite green while comparing nothing), and uploads the snapshot directory as the visual-baselines artifact to commit. When a slice intentionally changes the look, refresh the baselines inside that same slice.
