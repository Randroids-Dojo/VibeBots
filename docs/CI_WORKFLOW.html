CI Workflow

This document records the VibeBots CI policy for fast parallel development without reducing the release bar.

Principles

  • Cancel superseded work. A newer push to the same branch or pull request cancels older CI for that ref.
  • Run independent gates in parallel. Dash, purity, whitespace, lint, type-check, unit tests, build, and smoke should not wait behind each other unless they depend on the same artifact.
  • Keep every push covered by a small critical smoke set.
  • Run the full Playwright smoke matrix on a schedule and by manual dispatch, and run it locally when a risky slice touches broad UI behavior.
  • Track the latest remote tip. If a pushed commit is included in a newer origin/main tip, stop waiting on superseded runs and verify the current tip instead.

Required Push Gates

For pushes to main and pull requests, the required gate is the parallel CI set:

  • quality: dash check, sim purity, whitespace check, and Biome lint.
  • typecheck: Next route type generation and TypeScript.
  • unit: Vitest unit and route tests, followed by the deterministic golden suite.
  • build: one production Next build, exact-SHA runtime artifact, case inventory, duration-balanced functional plan, route inventory, and advisory bundle comparison.
  • e2e-critical: sharded Playwright smoke over the critical routes.

The critical smoke set lives in package.json as pnpm test:e2e:critical. It covers account sign-in entry, latest release notes, save-slot load refresh, and the deterministic mine dig loop. Render-dependent bunker-claim entry, fatal-fall, and mine-motion assertions remain in the render tier instead of the required software-rendered gate.

E2E shards use Playwright's test-level sharding with ONE worker per shard, for both Critical and Full E2E. The parallelism comes from separate shard jobs, never workers inside a runner, because the software-rendered suite is CPU-bound: two workers on the 4-vCPU runner make each SwiftShader render compete for CPU and starve rendering-dependent tests into multi-minute timeouts (a two-worker Full E2E dispatch failed ~60 tests, including specs that pass at one worker in the required Critical gate). The Full E2E matrix instead uses many shards (see Full Smoke below) so each shard is small enough to finish at one worker inside the budget.

These five are the whole merge gate (2026-09-02). The required status contexts on main are exactly the job names Quality, Typecheck, Unit Tests, Build, Critical E2E (1-of-2), and Critical E2E (2-of-2). Zero approving reviews are required and no review service is a required check. Preview Smoke (advisory), the Functional Shadow shards and summary, and the render tier stay advisory. PRs merge through auto-merge as soon as those contexts are green; see docs/WORKING_AGREEMENT.html §Mainline Integration. The ruleset changes that enforce this list are owner actions recorded as Q-038.

Mainline Health Tripwire

Everything that is not a required merge context is a post-merge tripwire. .github/workflows/mainline-health.yml runs on every completed CI and Browser Runtime workflow run on main (the workflow_run filter matches the workflows' name: fields, so renaming either silently detaches the watcher) and on manual dispatch. It re-evaluates the whole state on every trigger rather than trusting the triggering event, so out-of-order completions cannot leave a stale verdict.

Signals, each judged by its newest completed run on main:

  • ci.yml with event push: the required gate on the merged tip. A cancelled conclusion here means a newer push superseded the run and is skipped.
  • ci.yml with event schedule or workflow_dispatch: the Full E2E matrix. Push runs never execute it, so it is evaluated separately; a cancelled conclusion is RED (a shard that ran out of its job budget, F-131). This is the automated form of the Scheduled Run Visibility check below.
  • browser-runtime.yml with event push: the pinned browser image build. Path-filtered, so usually vacuously green.

While any signal is red the workflow keeps exactly one open issue titled Red main: mainline workflow failure with the label red-main, appending a comment for each further red completion, and closes it with the green run links once every signal's latest completed run is green. Agents check gh issue list --label red-main --state open at every session start (AGENTS.md Rule 5 step 2); an open issue preempts all new work and is repaired fix-forward through a PR, never by revert, force-push, or bypass. After a Full E2E repair lands, re-dispatch the matrix (gh workflow run CI -f full_e2e=true) so the signal clears without waiting for the nightly cron.

Dry runs: dispatch the workflow with mode=simulate-failure and then mode=simulate-success. Both use the red-main-test label so the real signal is untouched, and together they prove the create, comment, and close paths. Production deploy status is not yet a watched signal (F-240); until it is, the session-start check reads the production deployment for the origin/main head directly.

Full Smoke

The full Playwright smoke suite still exists as pnpm test:e2e. CI runs it in thirty-two shards, one worker each, 35-minute budget, for nightly scheduled runs and manual workflow_dispatch runs with full_e2e enabled. Sizing history: the original 4 shards / 1 worker / 20 minutes carried ~52 tests per shard at ~2 minutes apiece and completed only ~8 before the budget expired, timing out and cascading to red for a week; 8 shards / 2 workers / 30 minutes finished inside budget but the two-worker CPU contention starved ~60 rendering-dependent tests into timeouts; 16 shards / 1 worker / 35 minutes removed the contention (unique failures fell to ~30, all shards 6 to 15 minutes) but two shards holding clusters of slow software-rendered specs ran long; thirty-two shards of ~6 tests keep even a slow-cluster shard well inside the budget. Parallelism scales by shards, never workers or a bigger per-test cap, when the software renderer is the bottleneck. F-131 made the timeout visible; F-132 owns the deeper renderer-speed work.

Local pnpm test:e2e uses two file-level workers by default. Route-owned specs such as arena, workshop, routes, and API smoke can run beside focused mine feature specs such as core, bunker, viewport, save-slot, surface navigation, UI, and transport coverage. Keep canvas-heavy mine tests file-owned and avoid test-level mine concurrency unless intentionally stress-testing with PLAYWRIGHT_WORKERS=<n>.

Run the full suite locally or through manual dispatch before merging work that changes shared UI shell behavior, cross-route storage state, release-note infrastructure, Playwright harness behavior, or other broad surfaces where the critical set is too narrow.

Scope (2026-09-03). The hosted Full E2E matrix runs the @functional cases only (--grep "@functional"), the same selection the Critical gate and the Functional Shadow use. The @render, @visual, and @soak cases are owned by the real-renderer tier below, because SwiftShader is not the oracle for them: run on hosted runners they failed every night for sixteen nights (finding 5 of the 2026-09-01 session, red-main issue #360) while the same cases passed on the Mac tier, and the 2026-09-03 dispatch on the landed main (run 33716830154) had nine red shards whose every failing case was @render except one known functional flake. A hosted red therefore means a functional regression or a listed flake, never a renderer contract.

Internal deadline and evidence (F-131). Each Full E2E shard has a 35-minute GitHub job budget. Before the tests run, the job computes a Playwright globalTimeout from the budget still left after checkout, install, and build, reserving 150 seconds for teardown, the HTML/JSON report, and the artifact upload, and injects it as E2E_GLOBAL_TIMEOUT_MS (parsed by src/lib/playwright-global-timeout.ts). A slow or hung shard therefore STOPS itself as a normal Playwright failure with a written report instead of being cancelled at the job deadline with zero artifacts. The upload step (if: failure()) then runs and retains playwright-report/ (HTML plus results.json) and test-results/ (traces and screenshots). This deadline is unset for local runs and Critical E2E, which run unbounded. To prove the path, dispatch the workflow with a low full_e2e_global_timeout_ms (for example 30000): every shard times out fast and the run concludes failure with artifacts, not cancelled. What that low-value proof shows is exactly the failure-not-cancel plus upload-runs mechanism; the retained artifact is playwright-report/ (HTML plus results.json) and one error-context.md, because a 30-second budget expires during startup before any test runs. Per-test evidence depends on tests actually running: a test that FAILS before the deadline captures a screenshot (screenshot: only-on-failure, taken on the first attempt) and, on its retry, a trace (trace: on-first-retry); a test still mid-run when the hard whole-suite deadline interrupts it may have neither, which is an inherent limit of a hard stop, not something a trace mode can guarantee. The precise evidence guarantee is therefore narrower than "always has traces": the run always fails red (never cancels), the if: failure() upload always runs, and it is never empty (a pre-upload step writes a NO-REPORT.txt marker if the HTML report is somehow absent), so a timed-out matrix always leaves a named, downloadable signal to triage, plus per-test screenshots and traces for whatever failed before the deadline.

Stable Case Inventory

Every Playwright case carries exactly one stable case-id annotation and exactly one capability tag: @functional, @render, @visual, or @soak. Titles, filenames, and line numbers remain descriptive context only. They do not control CI routing.

pnpm ci:inventory discovers the live Playwright suite and validates missing or duplicate IDs, missing or multiple capabilities, unknown tags, pixel assertions inside @functional, @critical outside @functional, stale quarantine entries, quarantine capability drift, and expired or overlong quarantine deadlines. The command has no hardcoded test count. Its count comes from Playwright discovery, so adding or removing a case changes the inventory instead of bypassing it.

The live inventory contains 202 cases: 128 functional, 64 render, 3 visual, and 7 soak. CI uploads the generated inventory with discovery timing. Browser jobs also emit one bounded timing record per case attempt so later duration-based sharding uses measured stable identities.

The required Critical E2E command selects @critical and @functional together. Its four Stage 0 cases are E2E-ACCOUNT-0001, E2E-MINE-CORE-0002, E2E-MINE-SAVE-SLOTS-0002, and E2E-RELEASE-NOTIFICATIONS-0001. Pixel, renderer, and elapsed-frame assertions cannot enter the required subset through a title edit.

Build Once and Functional Shadow

The required Build job runs on Node.js 22.22.1 and creates one compressed runtime artifact for github.sha. Artifact creation refuses a dirty checkout before running next build. The archive contains the production .next output without its disposable cache, public, package.json, pnpm-lock.yaml, the exact case inventory, the functional shard plan, and ci-build-manifest.json. Source-loaded build configuration is intentionally absent so the built runtime starts from the config captured in .next. Retention is three days because this is a test input, not a release artifact.

The build manifest records the source SHA, clean state, lockfile SHA-256, pinned browser image digest, Node.js, pnpm, Next.js, Playwright, and Chromium versions, build timestamps and duration, all emitted routes, the runtime output size, and an advisory comparison against ci/bundle-baseline.json. Every consumer validates the archive path list, manifest schema, workflow SHA, lockfile hash, and browser image digest, extracts into disposable staging, then copies only the runtime and plan allowlist. The archived package and lockfile remain verification evidence and cannot overwrite the checkout's dependency inputs. A mismatch stops before Playwright starts.

ci/functional-duration-baseline.json keys timings by stable case ID. The initial source is Full E2E run 30008144077; a case uses its median successful attempt, while eleven cases with no successful sample use the existing 60-second per-test cap as a conservative fallback. pnpm ci:functional-plan applies deterministic longest-processing-time-first bin packing across ten shards. The current plan covers 128 unique functional IDs and 128 unique test-level selectors exactly once, predicts 303,628ms to 304,295ms per shard, and uses one Playwright worker in the pinned software-rendered runtime. The first eight-shard shadow run completed every job below ten minutes but put the slowest job at 9:59, so ten shards replace that trial map before mainline observation to preserve useful variance headroom.

The ten Functional Shadow jobs download and verify the one build artifact, install dependencies, and run exact file:line selectors from the reviewed plan. They never call next build. Test failures remain advisory during the minimum five-mainline-commit overlap, but missing reports, incomplete or duplicate discovery, a wrong commit, an invalid artifact, or other infrastructure failure remains red. Functional Shadow Summary combines every attempt, proves all 128 IDs were observed, reports outcomes and per-shard test time, and uploads a retained JSON summary. The existing Critical E2E job and scheduled Full E2E matrix remain unchanged during overlap.

Pull-request trial 30057283729 built workflow SHA 918bc4a63e2206b51eaf43e8e8438fded2c27815 once in 28,360ms and emitted all 58 routes with zero bundle-baseline delta. Its ten shadow jobs observed all 129 functional IDs in 139 attempts. The retained summary reported a p95 aggregate shard duration of 480,538ms by summing per-attempt test durations within each shard; this diagnostic is neither an individual-test percentile nor wall-clock job completion. Complete job durations ranged from 254 to 549 seconds. Promotion uses p95 measured complete-job duration across at least five mainline observations, while the aggregate detects duration-map and retry drift. Attempt outcomes were 119 passed, 10 timed out, 9 otherwise failed, and one skipped; those known renderer-hosted application outcomes remained advisory, while complete discovery and artifact integrity passed. The preceding eight-shard trial reached a 599-second maximum job, so the ten-shard plan is the observed overlap baseline.

Real Renderer Tier

pnpm ci:render -- --sha <commit> verifies renderer-owned behavior on the local Apple Silicon Mac instead of treating GitHub's SwiftShader timing as a product oracle. The command resolves and checks out the exact commit into a dedicated clean directory, installs from the lockfile, builds once, launches Chromium with one worker on a randomly selected isolated port, blanks application secrets, and refuses dirty source or checkout state. It never reads .env files and never reuses another agent's server. An exclusive owner lock covers checkout, dependencies, build, browser execution, and result publication. A second manual or scheduled invocation fails visibly instead of switching the shared checkout or mutating shared build output. A lock left by a dead process is recovered on the next invocation.

The default render tier runs every @render case. --tier all opts into render, visual, and soak together. --tier visual runs the committed platform screenshots, and --tier soak runs long-form stability coverage. Every execution writes a bounded result.json below ~/.codex/ci-render/vibebots-real-render/results/<sha>/, including a run that fails during setup. Every record carries schema version, commit SHA, source, status, timestamps, time zone, date key, and missed schedule windows. A run that reaches the browser also carries the environment fingerprint and per-tier test counts and attempts; a run that fails earlier carries an error message instead, and is filed under results/unresolved/ when it failed before the SHA could be resolved. latest.json points to the newest manual or scheduled result, while heartbeat.json is written only by a scheduled run so a manual check cannot hide a missed daily window. The fingerprint includes macOS, architecture, browser, viewport, device pixel ratio, and the active ANGLE renderer. A case that fails an initial attempt fails the tier even if Playwright's retry passes, so the real-render lane cannot normalize a flake into green.

A local Codex automation starts the physical-render exact-main check daily at 5:30 AM America/Chicago time with --scheduled --tier render. It runs from a dedicated clean source clone at ~/.codex/automations/vibebots-real-render/source, fetches origin/main, switches to that exact detached commit, proves HEAD equals origin/main, and installs from the lockfile before invoking the runner. It never reads or changes the developer checkout. It reports the exact SHA, environment fingerprint, artifact path, and any missed windows without creating a branch or merging. Visual and soak tiers use the same runner on demand. GitHub continues the existing overlap until the functional shadow has at least five mainline observations and the staged promotion criteria in the rewrite plan are met.

Deterministic Goldens

pnpm test:goldens runs versioned, browser-independent combat, mining, economy, replay, and world-snapshot vectors from tests/goldens/vectors. Every vector has a stable ID, seed, step count, action log, complete gear or design inputs where applicable, SIM_VERSION, MINE_VERSION for mine rules, a final FNV-1a snapshot hash, and selected semantic outcomes. A mismatch reports the vector inputs plus field paths and old and new values.

Golden output is updated only with pnpm test:goldens:update -- --reason <text>. The updater refuses an empty reason and refuses changed output while the relevant version constant is unchanged. Accepted updates append a machine-readable entry to tests/goldens/change-manifest.json, and each changed vector links to that entry. Tests reject a vector whose expected hash, semantic outcomes, changed-field list, prior result, or version no longer continues the manifest history, including a hand-edited baseline whose manifest version does not advance. A relevant version bump with no covered output change emits a review warning so unnecessary bumps or missing coverage stay visible.

The required golden job runs on Ubuntu 24.04 with Node.js 22.22.1. Exact hashes and floating-point comparisons are authoritative only in that pinned CI environment; changing either pin is a reviewed baseline event.

Scheduled Run Visibility (F-047)

A red nightly full-matrix run must be visible to the next agent without anyone listing workflow runs by hand. Since 2026-09-02 the Mainline Health Tripwire above evaluates this signal automatically and surfaces it as the red-main issue that Rule 5 step 2 in AGENTS.md checks at every slice start. The manual command below remains the fallback when gh cannot read issues or before the first health evaluation has run after adoption, and its filtering rules are the ones the watcher implements. Filter by --event schedule on the server rather than a client-side select over the default page: scheduled runs are rare, so a day of push and PR runs pushes the newest schedule run past the default 20-run page and a select(.event == "schedule") pipe then returns null (an empty result reads as "no red", the exact failure this gate exists to prevent). Also filter --status completed, so a queued or still-running schedule run (null conclusion) cannot mask an older completed red one:

gh run list --workflow CI --event schedule --status completed --limit 1 \
  --json conclusion,createdAt,databaseId,headSha

If the newest completed scheduled conclusion is failure and less than a day old, triage before picking a slice: inspect the failed jobs (gh run view <id> --log-failed), and if any failure is outside the known-flake list below, the regression IS the next slice. A known-flake-only red gets one line in the current slice's progress entry naming the run id, so the rot is on the record.

Timeout cancellations are red (F-131). A scheduled run whose conclusion is cancelled is red and must be triaged the same way. Evaluate the conclusion after fetching the newest completed schedule run; do not try to fold the conclusion into the list filter, because a matrix where some shards failure and others cancelled still rolls up as one run you must inspect. Supersession here is Full-E2E-specific, ancestry-based, and stricter than the push-run closeout rule: a push or PR run on a newer main SHA does NOT supersede a scheduled timeout, because push and PR gates never run the Full E2E matrix, so a newer green push proves nothing about Full E2E. A red scheduled run is superseded only by a later run that actually COMPLETED the Full E2E matrix (a newer scheduled run or a full_e2e manual dispatch) on a commit that CONTAINS the red commit as an ancestor (git merge-base --is-ancestor <red-sha> <newer-sha>), not merely a chronologically or numerically newer SHA. Until such a completed matrix exists and is green, a non-superseded cancelled or failure conclusion on the newest completed schedule run stands and must be triaged.

Known Full E2E flakes (fail intermittently on unmodified main; do not chase inside unrelated slices, but a slice may claim one deliberately; since 2026-09-03 the hosted matrix runs @functional only, so the @render entries here, the holodeck pinch-zoom and falling-rock camera specs, are the Mac tier's to watch): the holodeck pinch-zoom spec (holodeck.spec.ts REQ-021 camera test), the falling-rock camera spec, the raid-XP overlap retry spec (mine-bunker.spec.ts, a fix branch exists), the account-sync conflict-choice spec (mine-account-sync.spec.ts), and, as a candidate pending a second scheduled run, the bunker claim-mode spec (mine-bunker.spec.ts, mine requires an explicit bunker claim mode before showing the claim panel: a page.evaluate in the gamepad-back helper hangs to the 60 second test timeout and again on its retry, the Q-035 software-render stall signature; seen once, 2026-09-02, on a commit the previous day's run had passed; a repeat on an unchanged spec confirms it, a pass removes it; the same helper stall was seen 2026-09-03 in the mine-account-sync Escape-and-gamepad-back case on the non-required Runtime Shadow (hosted) shard of PR #354 head 1805415c, a docs-and-comment change, and passed on rerun; and again 2026-09-03 on the non-required Runtime Shadow (pinned) shard of PR #356 head 2de0bdf6, a copy-only change, both attempts at the 60 second timeout). First-person bunker pixel, telemetry, and movement checks are classified as physical-render contracts, not random flakes; the real-render tier now owns them while the hosted overlap remains visible. The bunker claim-edit fixture and Holodeck pause sampling defects were fixed in the real-render slice. Update this list when a flake is fixed or a new one is triaged.

Resizing history and the contention finding (2026-07-21): the first resize to 8 shards / 2 workers / 30 minutes fixed the timeout cascade (dispatch 29885827771 completed every shard in 3 to 28 minutes), but completing revealed the two-worker cost. A comprehensive scan of that run and its follow-up (dispatch 29889999826, which added the software-fallback DPR cap) showed ~68 then ~59 unique tests failing, dominated by mine, elevator, viewport, and fp specs, almost entirely with multi-minute timeouts (for example "Test timeout of 240000ms exceeded" on tests that finish in ~30s locally and at one worker in the Critical gate). That is CPU starvation from two SwiftShader renders sharing 4 vCPUs, not per-test flakiness. The fix reverted to one worker and doubled the shards to sixteen so each stays small enough to fit the 35-minute budget without contention. The software-fallback DPR cap (FallbackDprCap) stays, since faster frames help the one-worker path too. The residual after that is the genuine software-rendering flakes (holodeck pinch-zoom, account-sync conflict, a couple of fp pixel/telemetry specs), which remain F-132's deeper renderer-speed work.

Agent Behavior

  • Arm auto-merge on the required gate and move on. Do not wait for the merge, the preview deploy, or a bot review; the tripwire and the next session's health check own the merged tip.
  • Never revert, force-push, or bypass-merge to land work or to clear a red main. Repair lands as new commits through a PR.
  • When repairing a red main or checking a deploy, track runs by run id and head sha, not by branch name. If the remote tip advances and still contains the commit, follow the newest tip's checks, not the older superseded run; if it does not contain the commit, stop and reconcile.
  • Do not wait on cancelled, superseded, or older in-progress runs once a newer verified remote tip contains the commit being closed out.
  • Do not point the standard Playwright suite at protected production Vercel URLs with PLAYWRIGHT_BASE_URL. Use local or CI Playwright for app behavior, and use GitHub deployment status plus Vercel metadata for production deploy readiness.

Visual Regression Baselines

The full smoke suite includes tests/e2e/visual-baselines.spec.ts: paused Block Gallery scenes (terrain and classic ores), clipped to the block rows and screenshotted against committed per-platform baselines with toHaveScreenshot (maxDiffPixelRatio 0.02). The clip excludes the miner: its time-driven emissives (chest screen, visor, beacon) never pixel-stabilize, which fails Playwright's stable-capture check. Linux and macOS baselines are committed, including the Apple Silicon Mac runner images used by the real-render visual tier. Tests skip only when the running platform has no reviewed baseline.

Bootstrap or refresh: dispatch the CI workflow with update_visual_baselines=true. The dedicated job rebuilds, regenerates the snapshots with UPDATE_VISUAL_BASELINES=1 and --update-snapshots (the env opt-in exists because Playwright's default missing-snapshot policy silently writes and passes, which would make an uncommitted suite green while comparing nothing), and uploads the snapshot directory as the visual-baselines artifact to commit. When a slice intentionally changes the look, refresh the baselines inside that same slice.
