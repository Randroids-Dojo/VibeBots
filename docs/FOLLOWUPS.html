Followups

Backlog spillover discovered during implementation. Keep items PR-sized when possible.

Critical convention. Every followup must carry a data-priority attribute. Three buckets:
  • blocks-release: cannot ship v1 without this.
  • nice-to-have: improves the product but does not block.
  • polish: post-release cleanup.

How to add a followup

<section data-f="F-NNN" data-priority="blocks-release|nice-to-have|polish">
  <h3>F-NNN: Short title</h3>
  <dl>
    <dt>Context</dt><dd>one or two sentences on why this came up.</dd>
    <dt>Blocker (if any)</dt><dd>the condition that prevents working on this now.</dd>
    <dt>Unblock condition</dt><dd>what has to be true to start.</dd>
    <dt>PR / Dot reference</dt><dd>#N or dots-N (when picked up)</dd>
  </dl>
</section>

Keep F-NNN IDs monotonically increasing. When a followup ships, leave the entry in place and append a <dt>Resolved</dt><dd>PR #N</dd> entry. Never delete.

F-004: Rate limiting on match resolution (Upstash Redis)

Context
Server-side match resolution burns real CPU; abuse becomes plausible once matches are public. VibeKit ships a fixed-window rate limit over Redis.
Blocker (if any)
one-backing-store rule (AGENTS.md Rule 11): launch storage is a single dedicated Neon Postgres.
Unblock condition
real traffic on the match-resolve API makes abuse concrete; then provision a dedicated Upstash Redis via the marketplace UI.

F-003: Clerk sign-in upgrade over guest auth

Context
Fun-first path is guest identity via a VibeKit-signed httpOnly cookie (zero signup friction). Clerk (native Vercel marketplace integration) adds cross-device accounts later; the players table carries a nullable clerk_user_id from day one so guest rows can be claimed on first sign-in.
Blocker (if any)
guest auth and the players table do not exist yet.
Unblock condition
guest-auth slice ships and cross-device persistence starts to matter.

F-002: Vercel Workflow for match orchestration

Context
Single-match resolution fits a plain Fluid function with maxDuration. Vercel Workflow (durable steps, retries) is the right shape for multi-step pipelines: queue match, simulate, persist replay, update leaderboard, grant rewards, and batch tournaments.
Blocker (if any)
no multi-step match pipeline exists yet.
Unblock condition
match resolution grows beyond one request/response (tournaments, reward fan-out) or outgrows the function duration budget.
