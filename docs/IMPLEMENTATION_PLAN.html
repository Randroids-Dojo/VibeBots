Implementation Plan

This document is the main operating loop for VibeBots implementation. Agents must keep working continuously until the planned scope is complete.

Loop Contract

Every slice follows the same loop:

  1. Read AGENTS.md, README.md, this plan, docs/WORKING_AGREEMENT.html, the relevant docs/gdd/ files, docs/PROGRESS_LOG.html, docs/OPEN_QUESTIONS.html, docs/FOLLOWUPS.html, docs/GDD_COVERAGE.json, docs/DEPENDENCY_LEDGER.html, docs/MAINLINE_REVIEW_LOG.html, docs/CI_WORKFLOW.html when touching CI, verification, or release process, and the active backlog.
  2. Check mainline health. gh issue list --label red-main --state open, plus the production deployment status for the origin/main head. If main is red, the repair is this session's slice and nothing else is picked until the issue closes (fix forward only).
  3. Run the Dependency Upgrade Gate (see below). If a watched dep is out of date, the upgrade is the next slice unless step 2 (red main) takes over.
  4. Run the post-merge adversarial review when the cursor in docs/MAINLINE_REVIEW_LOG.html is behind origin/main: review every squash commit since the cursor, file findings as followups or open questions, confirm merged PRs' backlog items carry their PR numbers, and append a log entry.
  5. Pick the highest-priority unblocked task from this plan, coverage gaps, followups, the qualitative-gate docs, and the active backlog.
  6. Claim it. Check for an existing claim (open PRs and remote branches naming the id or slug), then create one branch for one PR-sized slice from fresh origin/main, push it, and open a draft PR whose body starts with Claims: F-NNN (or the Q-id, or none plus a one-line scope).
  7. Build the slice completely using existing code patterns.
  8. Add or update tests for the touched behavior.
  9. Update continuity docs and the GDD coverage ledger, and close the backlog item with the PR number in the same diff.
  10. Run local verification (pnpm verify, --build for runtime-affecting slices). Run the full Playwright smoke suite locally or by manual dispatch when the touched surface warrants it; the merge gate does not run it.
  11. Re-run the Dependency Upgrade Gate before marking the PR ready. If a watched dep landed a new release while the slice was in flight, defer it to a separate PR (do not bundle into this one); log the bump as the next slice.
  12. Mark the PR ready and arm auto-merge with a validated squash subject and body (gh pr merge <number> --auto --squash). The five required parallel CI contexts are the only merge gate. Do not wait for the merge, the preview deploy, or a bot review.
  13. If a human leaves review comments on the open PR, fix what is valid, reply when useful, resolve threads, and re-arm auto-merge if it dropped.
  14. Immediately start the next slice at step 1. Step 2 of that pass is where a merge that broke main becomes visible.

Do not stop after planning, after opening a PR, or after arming auto-merge. If a task is blocked, log the blocker in docs/OPEN_QUESTIONS.html or docs/FOLLOWUPS.html, update the backlog item, and move to the next unblocked slice.

The standing decision behind this loop is docs/WORKING_AGREEMENT.html §Mainline Integration. Its owner-side prerequisites (ruleset and auto-merge settings) are tracked as Q-038; until they are executed, step 12 falls back to merging on green yourself, still with no bot wait.

Dependency Upgrade Gate

Run at two points in the loop:

  • At step 3 (session start on fresh main, after the mainline health check), before picking the next slice.
  • At step 11 (before marking the PR ready), to catch new releases that landed while the slice was in flight.

Read docs/DEPENDENCY_LEDGER.html. For every watched dep, run its Detect-new command and compare against the ledger's Currently pinned value. If a newer release exists:

  1. The upgrade IS the next slice unless slice selection priority 1 (red main) takes over.
  2. Follow the per-dep procedure in docs/DEPENDENCY_LEDGER.html §Upgrade procedure: branch, bump, type-check, test, build, smoke, PR.
  3. If the upgrade requires a migration that cannot land in one PR, abort the bump, log an F-NNN followup for the migration work, and continue with the prior pin. Add a Dot for the migration work.
  4. The bump PR updates the ledger's Currently pinned line in the same diff that bumps the package manifest. The two must move together.

The gate is mechanical, not optional. A new pinned tag is the same kind of "fresh state" that a new commit on main is: the agent must observe and react.

Slice Selection

Priority order:

  1. Red main: an open red-main issue (any watched mainline signal red, including the nightly Full E2E matrix), a failed production deploy for the origin/main head, or a red required gate on the merged tip. Repair is fix-forward through a PR.
  2. Pending dependency upgrades from docs/DEPENDENCY_LEDGER.html.
  3. Active P0 or P1 backlog items.
  4. Open docs/OPEN_QUESTIONS.html entries that block implementation and have enough information to resolve.
  5. High-priority docs/FOLLOWUPS.html items.
  6. docs/GDD_COVERAGE.json gaps marked not_started or partial.
  7. GDD requirements with user-visible scope still marked partial.
  8. Once coverage is ≥80% done: open items in docs/PLAYTEST.html and gaps in docs/FUN_FACTOR_AUDIT.html. These are the second gate. The loop is not finished until these resolve.
  9. Cleanup that removes blockers, stale docs, or brittle test gaps.

Prefer the smallest slice that creates a useful PR. Avoid mixing unrelated work.

Definition Of Done

A slice is done only when all apply:

  • Code, docs, tests, and coverage ledger match the implemented behavior.
  • Required local verification passes.
  • The claim PR is ready (not draft), any human review comments are handled, and auto-merge is armed with a validated squash subject and body (or, while Q-038 is open, the PR was merged on green by the session).
  • The required parallel CI gate is green on the PR head. Auto-merge lands it; the session does not wait.
  • The backlog item or followup is closed with the PR number and verification in the slice's own diff.
  • If the merge turned main red before the session ended, the repair slice is also done. Otherwise the next session's health check owns it.

Merge, deploy, and production smoke are no longer waited on inside the slice. The mainline health tripwire and the next session's step 2 own them.

Project Closure

The loop ends when ALL apply:

  1. Every row in docs/GDD_COVERAGE.json is done with implementation and test refs.
  2. Every checklist item in docs/PLAYTEST.html is checked or explicitly deferred to a follow-up release.
  3. docs/FUN_FACTOR_AUDIT.html has been re-run after the last system landed and produced no new P0 or P1 gaps.

Closing the loop without all three is the Flatline failure mode: shipping a complete-on-paper system that is not actually good.
