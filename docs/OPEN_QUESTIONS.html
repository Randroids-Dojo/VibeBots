Questions here block or influence implementation.

Critical convention. Every question must include a <dt>Recommended default</dt> entry. The loop ships under that default and leaves the question open for override. Do not block the loop on dev sign-off. Stress-tested values that survive multiple iterations get frozen.

Q-028: How should the elevator outcome outbox be drained without a cron?

Context
The durable elevator outbox (F-121) records one elevator_upgrade_outcomes row per buy, committed atomically with the charge, and delivers the structured monitoring event separately (emit-then-mark, at-least-once). A crash between commit and delivery, or a sink outage, leaves rows with delivered_at IS NULL that must be redelivered. The project has no cron or scheduled-job infrastructure (no vercel.json crons, no cron routes).
Options
  1. Drain opportunistically on request traffic: each elevator request first delivers a bounded batch (20) of stranded rows older than a 30s grace, best-effort.
  2. Add a Vercel cron hitting a new maintenance route that calls the drain on a schedule.
  3. Deliver inline only, no recovery drain (accept that a crash-stranded outcome is lost).
Recommended default
A. It needs no new infrastructure, is trivially testable, and delivers every stranded outcome as long as elevator traffic continues (buys are the only thing that creates rows, so traffic that creates a stranded row is exactly the traffic that later drains it). The added cost is one bounded indexed query per buy, on an infrequent action. C loses outcomes on a crash, defeating the durability the item requires. B is the cleanest at scale but adds cron infrastructure this project does not yet have; the drain function (drainPendingElevatorOutcomes) is already factored so a future cron can call it verbatim without changing the contract. Revisit and adopt B if elevator traffic ever becomes bursty enough that stranded rows sit undelivered for long between buys.
Status
open
Resolution
Shipped under default A (the loop convention: ship under the recommended default and leave the question open for override). The durable-outbox slice drains the outbox opportunistically on elevator request traffic; the drainPendingElevatorOutcomes function is factored so option B (a cron) can call it verbatim later without any contract change. Left open so the cron option can be adopted if traffic ever becomes bursty enough that stranded rows sit undelivered for long between buys.

Q-027: Should the elevator buy require the client's expectedDepth?

Context
expectedDepth is the stale-rail guard on /api/elevator/upgrade: the route rejects a buy whose expected rail depth does not match the stored depth, which is what stops a stale or replayed buy (a retry after a lost success response) from silently advancing a second row (F-121). It was kept OPTIONAL for backward compatibility while clients rolled it out, so a request that omits the field bypasses the guard entirely. Every current client sends it (the store passes the live rail depth, 0 for the first rail), so the only requests without it are stale cached clients, which are exactly what the guard exists to reject. Making it required is a maintainer policy call because it could, in principle, break a genuinely old cached client mid-session.
Options
A. Require it with a stable fail-fast 400 (proposed default): reject any request without expectedDepth before any read or charge, and tighten the client so it can never be omitted. B. Keep it optional indefinitely, accepting that a request without it bypasses the stale guard. C. Require it but with a grace period (accept-and-warn) before enforcing.
Recommended default
A. All current clients send it, so no legitimate live request is rejected; a stale cached client from before the field existed now gets a clear 400 and reloads to the current client rather than silently buying a second row against a bypassed guard, which is strictly safer than the prior silent bypass. B leaves a permanent hole in the guard the whole item exists to close. C adds accept-and-warn plumbing for a cohort (pre-field cached clients) that a single reload eliminates, for no safety gain over A. Revisit only if telemetry shows a meaningful volume of legitimate no-expectedDepth traffic after release.
Resolution
Shipped under default A (branch fix/elevator-expected-depth-required): the route rejects a missing expectedDepth fail-fast with the stable code elevator-expected-depth-required (400), and buyRemoteElevator's signature makes it required and always sends it (including 0). See F-121 and the progress log.

Q-026: May a Start fresh bunker take legacy whole-cell parts before slot placement ships?

Context
F-117 slice 3 (package 0.1.271) lands the layout-version boundary and a confirmed Start fresh, which detects an old bunker by its persisted layout_version and, on Start fresh, clears the built parts and stamps the current version. But the first-person builder still emits no slot (slot placement is a later slice), so a bunker that was just Started fresh is stamped current yet the only parts a player can place into it are still legacy whole-cell parts. Because incompatibility is detected by version and the bunker is now current, it never fails fast again, so a current bunker can accumulate legacy parts in the interim between this slice and the slot-placement slice.
Options
A. Allow it (proposed default). Keep the slice minimal: fp part-building continues with legacy parts on current bunkers, and the slot-placement slice retires legacy placement while letting any legacy parts already present coexist with new thin parts, no second reset. B. Block legacy placement on current bunkers now, pausing fp part-building (digging still works) until slot placement ships, so no legacy parts can enter after a Start fresh.
Recommended default
A. It keeps building usable between slices for the two alpha players and is safe: no persisted slot write happens before the slot-placement slice (the exact boundary the whole F-117 arc is sequenced around), and no second no-refund reset is needed because slice 2 already made legacy whole-cell parts and thin parts coexist. A single cell cannot hold both (a whole-cell part blocks every thin slot in its cell and vice versa, enforced symmetrically), so a current bunker holding some legacy-part cells and some thin-part cells is structurally coherent; the player swaps legacy for thin over time by prying, with no forced wipe. B would leave the bunker dig-only for an unknown number of releases, a worse experience with no safety gain given the coexistence. Revisit only if the slot-placement slice slips far enough that carrying legacy parts becomes a real content risk.
Forward compatibility (2026-07-16)
A review of slice 3 asked what happens to a bunker whose persisted layout_version is above the deployed build's current version (an old build reading a row a newer build wrote, for instance during a rollback). Deferred to when a version 2 actually exists, for two reasons. First it is unreachable today: no code writes a version higher than the single current one, and the marker is stamped server-authoritatively, so no row can carry a future version. Second the destructive path is already safe against it without new code: Start fresh only proceeds when a bunker is below the current version and no-ops on any bunker at or above it, so a hypothetical newer bunker can never be downgraded or wiped by this build. What remains for the version-2 slice is a dedicated read-only "update your app" state (distinct from the destructive Start fresh, which must never be offered on a newer generation); building that state now, with no newer generation to test it against and no defined newer-version recovery UX, would be speculative scaffolding.
PR / Dot reference
(pending) resolving under default A in the F-117 slice-3 PR (package 0.1.271).
Resolution (2026-07-18)
Closed under default A, as proposed. The interim ran exactly as planned across the slot-placement and thin-geometry slices, and the full-cell retirement slice now removes the last legacy path: in first person a sealing part (wall, floor, roof, door) requires a matching slot on the aimed face, so aiming it where it has no slot is rejected outright instead of dropping in a legacy whole-cell block (placeOk now requires placement.valid). The fp builder therefore no longer emits a whole-cell sealing part at all. Q-024: How authoritative is in-raid player movement?

Context
The 2026-07-13 design pass had Clankers hunt the player's real 3D cell, with reaching the player counting as a miner death. Making that honest with server authority would force the server to know or replay the player's movement (a per-tick trace or server-replayed inputs), plus deterministic browser/Node parity and a hostile-trace validation matrix (the weight behind F-104, F-110, and F-111). For an early-alpha, single-player-feeling bunker defense whose only reward is the owner's own defensive XP and vibes, that anti-cheat machinery costs far more than it protects. Dev direction 2026-07-15: do not overthink the anti-cheat. First read as "movement is cosmetic, defenses decide it" (option A), but the dev then clarified the intended feel: Clankers should eat through the blocks to breach, keep pushing toward the live player if they have energy left, spend energy destroying walls, lose extra energy crossing spikes, and die (animated) when energy runs out; if even one Clanker reaches the player the miner dies, with a lost dialogue resolved back at the surface. So movement genuinely matters, and "do not overthink the anti-cheat" means the client runs the raid and the server trusts a bounded outcome rather than replaying it (option D).
Options
  1. Client-only movement. The server resolves the raid from the frozen bunker-defense snapshot versus the seeded Clanker wave; walking around inside is visual and does not change the result. The server enforces only the lifecycle: one start that locks the bunker against edits, one snapshot-frozen resolve, and server-owned expiry so an abandoned tab still settles. The player is kept inside for the duration (no exit affordance), which needs no anti-cheat because the outcome is already defense-decided.
  2. Server-replayed tick inputs. The client sends its per-tick inputs, the server replays one deterministic cell-movement sim to derive every position, so dodging decides survival and cheating is impossible by construction. Strongest integrity, largest implementation (a deterministic sim, golden vectors, and a hostile-input matrix).
  3. Validated position trace. The client sends its trace and the server validates each hop is reachable. Middle ground with the biggest edge-case surface.
  4. Client-run raid, movement matters, light server validation (dev-chosen 2026-07-15). The client runs the real-time first-person raid: Clankers approach and chew through blocks to breach (each bite spends energy), then keep pushing toward the live player through the dug halls while energy lasts, spending more energy to destroy walls and losing extra energy to spikes they cross; a Clanker whose energy hits zero dies with an animation. If even one Clanker reaches the live player the miner dies and the raid is lost (death animation, lost dialogue, resolve at the surface). The client reports the outcome (defense wear, loot, XP, win or loss) and the server applies it against the frozen start snapshot with light bounds (within the authored duration, damage no worse than the snapshot's defenses allow), not a deterministic replay. Movement genuinely matters because dodging and leading Clankers onto spikes is how you survive; the anti-cheat is deliberately not overthought because with a handful of alpha players the only exploit is winning your own defense.
Recommended default
D (dev direction 2026-07-15, supersedes the earlier A read). It matches the intended feel, a tense first-person survival where both your layout and your dodging keep you alive, while still refusing the heavy server-replay arc the dev declined. The wave hunts the live player, so the lose condition is exactly "a Clanker reaches you", with no frozen-target substitute and no core re-introduction (F-118 stays). Rescope under D: F-104 becomes the client-run raid sim contract (energy-budget Clankers, chew-to-breach, hunt the live player, spikes drain energy, death on contact and on energy depletion, 3D XP pickups) plus the light server-validation bounds; F-105 through F-108 keep their lifecycle integrity (single resolve, bunker lock against edits, server-owned expiry and abandonment recovery, conflict resync, frozen start snapshot) because the server still owns start and settlement even though it trusts a bounded outcome; F-110 shrinks to bounding the reported-outcome payload (finite values, within-snapshot damage, one settle) rather than a whole hostile-trace matrix; F-111 is dropped because a client-authoritative outcome needs no browser/Node determinism parity. A is rejected: the dev wants movement to matter. B and C are the over-built anti-cheat the dev declined. Revisit if a future PvP or ranked mode raises the stakes enough to justify server authority.
Status
resolved 2026-07-15: option D (dev direction). The live-raid arc ships under D; F-104 reframed, F-110 slimmed, F-111 dropped, F-105 through F-108 kept.

Q-019: What happens when the player leaves a live first-person raid?

Context
Live first-person raids (design pass 2026-07-13) put the player inside the bunker while Clankers hunt their actual cell. Raids are autonomous once started and cannot pause, but the player can always exit the first-person mode (button, Escape, a closed tab, a dead phone).
Options
  1. Forfeit: the remaining ticks resolve player-absent with Clankers targeting the core; no survival reward; damage stands.
  2. Block exiting while a raid runs (trapped until it ends or the miner dies).
  3. Auto-survive with reduced rewards.
Recommended default
B with a forfeit-loss disconnect fallback (under Q-024 option D). Dev direction 2026-07-15 is that the player is kept inside until the raid ends, so the UI simply does not offer an exit while a raid runs. Because movement matters under D (surviving means dodging Clankers and leading them onto spikes until their energy runs out), an absent player cannot be treated as a survivor. The one real escape hatch is an involuntary disconnect (closed tab, dead phone): the server-owned expiry then resolves the raid as a forfeit loss, the miner counts as reached, damage stands, and no survival reward is granted.
