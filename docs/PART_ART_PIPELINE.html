Part Art Pipeline

How bot part geometry and materials are built, how to add or reshape a part without breaking the deterministic sim, and the workflow for driving 3D art work with the Fable 5 model. Established 2026-07-05 with the shaping overhaul (commit 4872965) that took parts from flat-shaded collider primitives to beveled, manufactured-looking components. Companion enforcement rule: .claude/rules/part-visuals.md. Related: docs/research/realistic-graphics-pipeline.html (the lighting/post roadmap) and docs/research/battlebots-design-reference.html (the classic-BattleBots silhouette reference that drives part shape and material direction).

1. The render / sim split (read this first)

Every part has two independent representations. Keeping them separate is the load-bearing idea of this whole pipeline.

  • The collider (shape in src/sim/parts.ts): one of {type:"cuboid",hx,hy,hz}, {type:"ball",radius}, {type:"cylinder",halfHeight,radius,axis}. This is the deterministic Rapier body. It drives physics, the layout solver, drag targeting, world snapshot hashes, and server-side replay. It is gameplay, not art.
  • The render mesh (src/components/part-geometry.ts + partGeometry() in part-visuals.tsx): the visual geometry drawn for that collider. This is art, not gameplay.

The rule that follows from this: shape parts by editing the render mesh only. Never touch a collider to change how a part looks. A collider edit bumps SIM_VERSION (Rule 3), changes match outcomes, and invalidates every saved replay {seed, design, simVersion}. There is no art reason worth that. If a look seems to need a different collider, that is a gameplay decision: log it in docs/OPEN_QUESTIONS.html and get sign-off.

2. Architecture

  • src/components/part-geometry.ts: pure three (no JSX, no React), so it runs in the node vitest env and is unit tested. Exposes partShapeGeometry(shape, category, detail) and the detail tiers HIGH_DETAIL / LOW_DETAIL. Internally it dispatches per collider type and category to a set of builders (see section 3), and caches every result in a never-disposed module map keyed by shape params + treatment + tier, so all meshes showing the same part share one BufferGeometry and the every-frame workshop turntable pays zero per-frame geometry cost.
  • src/components/part-visuals.tsx: the thin React seam. partGeometry(shape, category) resolves the current detail tier and returns a <primitive object={...} attach="geometry" dispose={null} />. It is used identically at four call sites, so one change upgrades everywhere: workshop PlacedPart, HeroPart (carousel), DragGhost, and the arena part render. Also holds CATEGORY_SURFACE (material params) and shapeRotation() (mesh-local reorientation matching a cylinder's axis).
  • Call sites pass def.category and set a meshStandardMaterial with the category color plus the emissive refs that animate selection (white glow) and merge (gold flash). Those refs are why the base material must stay meshStandardMaterial.

3. The geometry builders

Dispatch lives in buildShape(). Current treatments:

  • Rounded box (buildRoundedBox): a subdivided box whose corner vertices are pulled onto the fillet of an inset core box. Flat faces keep exact normals, edges get true fillet normals, so smooth shading gives crisp faces with a bright rolled-edge highlight. Per-category edge size (CUBOID_BEVEL): soft fillet on cores, machined chamfer on structure/mobility, tight edge-break on weapons.
  • Spike (buildSpike): elongated weapon cuboids (depth >= 2x the larger cross-axis) taper to a small flat tip. This is the Ram Spike and any future forward spikes. Mounts are +z, tip forward at -z (matching the cores' -z front).
  • Machined ball (buildMachinedBall): a lathe with polar mount-boss flats and an equatorial seam groove (two shells bolted together). Used for sensor / hammer heads.
  • Tire (buildTire, mobility cylinders): chamfered tread shoulders and a recessed hub with a raised lip on both faces. The recess shading separates rubber ring from hub with one material.
  • Toothed disc (buildToothedDisc, weapon cylinders): teeth cut into the rim via extrude with a thin bevel and an arbor hole. Teeth sit AT the collider radius, gullets carve inward, so the aimed silhouette matches physics.
  • Column (buildColumn, other cylinders): chamfered caps; slender spars like the mast get a thinner shaft between two full-radius collars.

Cylindrical builders build along local Y exactly like CylinderGeometry, so shapeRotation, layout, and drag targeting are untouched. Watch the three r185 LatheGeometry gotcha: it pushes an unnormalized normal for the last profile point, shading cap centers black. Every lathed form runs through a normal-repair pass (lathe()); reuse it for new lathed builders.

4. How to add or reshape a part

  1. Define or keep the collider in src/sim/parts.ts (gameplay-driven: mass, reach, connectors). Do not tune it for looks.
  2. Pick or add a builder in part-geometry.ts for that collider type + category. Keep all vertices inside the collider half-extents (carve inward). Add a cache key branch if the treatment is new.
  3. If the new treatment needs a category signal, it already receives category; thread any new param through partShapeGeometry and the cache key.
  4. Extend part-geometry.test.ts: it iterates the whole catalog at both tiers and asserts vertices in-bounds, finite unit-ish normals, and a triangle budget. New builders must pass it.
  5. Do not touch the four call sites unless you are changing the partGeometry signature. Do not re-add flatShading.
  6. Verify visually per section 6.

5. Materials, mobile, and performance

  • Base material is meshStandardMaterial (cheapest on the WebGL2 backend, preserves emissive refs). CATEGORY_SURFACE keeps identity legible: core glows soft and round, weapon is glossy tight-edged steel, mobility is matte rubber, structure sits between. Smooth shading lets metals be glossier because fillet edges carry the highlight instead of facet sparkle.
  • Detail is tiered off resolveGraphicsQualityTier(readStoredGraphicsQuality(), hasCoarsePointer()): LOW (coarse-pointer / forced-WebGL2 phones) uses fewer radial segments and box subdivisions, HIGH (desktop WebGPU) uses more. No isWebGPUBackend gate is needed for plain geometry; both backends chew it identically. Gate only actual render passes on the live backend (see graphics-quality.ts and the realistic-graphics-pipeline research doc).
  • Budget: keep each part under ~2000 tris. A full 10-part bot is ~4-6k tris (was ~1k), still one material per part, no textures, no extra passes, no per-frame allocation. Geometry is module-cached, so cost is paid once per unique shape.
  • Deferred, high-tier-only work (a future separate slice): sibling greeble meshes (bolt heads, an emissive core window) and a TSL procedural panel-line node material gated behind isWebGPUBackend + high tier. Keep the WebGL2 path free of it.

6. Verification checklist (before shipping any part-art change)

  • pnpm typecheck, pnpm exec biome check on the touched files, and no em/en-dashes (Rule 1).
  • pnpm exec vitest run src/components/part-geometry.test.ts (in-bounds + budget) and the full unit suite green.
  • Build, then pnpm exec playwright test arena.spec.ts workshop.spec.ts on an isolated port (Rule 9 local isolation). Render changes can throw at runtime; these render real canvases.
  • Screenshot the workshop part carousel and an arena match at desktop AND 390x760 Android portrait (project memory: validate mine/bot changes at 390x760). Eyeball every category: core, structure, mobility, weapon.
  • Confirm src/sim/parts.ts is unchanged in the diff and SIM_VERSION is untouched.

7. Driving 3D art with the Fable 5 model

The shaping overhaul was produced by delegating to the Fable 5 model (claude-fable-5, available via the Agent/Workflow model: 'fable' override) acting as an autonomous 3D technical artist. It performed well: it independently found and worked around the r185 LatheGeometry normal bug, chose fillet-baked normals, respected the render-only contract, and self-verified with Playwright and a vertex-budget test. Reusable recipe for the next 3D task:

  1. Spell out the hard constraints up front: render-only over unchanged colliders, three/webgpu with WebGL2 mobile fallback and a triangle budget, no new dependencies, keep category identity and the emissive refs, no dashes.
  2. Name the exact files to read (the four in section 2 plus sim/parts.ts and graphics-quality.ts), so it grounds in the real code instead of inventing an API.
  3. Demand a concrete deliverable format: an art-direction statement, drop-in code, a mobile-safety note, and a prioritized rollout. Tell it the final message is data for the lead engineer, not chat.
  4. Verify its claims yourself. It tends to over-deliver (it edits the worktree, not just proposes), so review the actual diff and re-run the full section 6 checklist before shipping. Do not trust a subagent's "tests pass" without rerunning them.
