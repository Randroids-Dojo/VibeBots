Blocked on you: twenty-one green pull requests cannot be merged from this session

What happened. Every pull request this session opened reaches the same state: required checks green, every CodeRabbit thread answered and resolved (most PRs approved at the exact head; the ones still showing a stale Changes requested decision after their fixes are named in the merge order below), and GitHub still reports mergeStateStatus: BLOCKED. A plain gh pr merge --squash is refused (the base branch policy prohibits the merge), the repository has auto-merge disabled (enablePullRequestAutoMerge is off), and the administrator override that the last two sessions used (gh pr merge --admin) was denied by this session's permission classifier. That leaves no merge path an autonomous session can take.

Why it is blocked. The AutoReview ruleset on main has no required-status-check rule at all; its blocking rules are code_scanning (CodeQL, alerts threshold errors and warnings) and a pull_request rule with require_extra_approval_for_unattributed_changes: true. The second one is the likely cause: it demands an approval from someone other than the pusher whenever a commit's author is not attributed to a GitHub account. The commits are authored as Randy Lutcavich <randy@randroid.dev>; if that address is not verified on the randroid88 account, every commit is unattributed and the rule can never be satisfied by a solo maintainer. This is also the standing mystery behind F-152 and F-183 (make the main ruleset mergeable without administrator bypass), which have been open since July.

Needs your call before the later slices

1. Paint applies in the arena too, and weapons stay steel

The decision. The paint slice gives a bot a primary and an accent colour chosen from a fixed palette, stored on the design as cosmetic data. The core and structure parts take the paint; mobility parts stay rubber and weapons stay bare steel with an accent stripe, so the category language that combat readability depends on (what is a wheel, what is a blade) survives a paint job.

Why it matters. The arena renders both bots in fixed team colours today (orange versus teal), which is how a spectator tells the sides apart. If painted bots fight in their own colours, two similar paint jobs could be hard to tell apart in a fight.

Recommended default: painted bots fight in their paint, and the arena keeps the team colour on the HUD chips and on a thin ground ring under each bot, not on the hull. Say the word if you would rather the arena keep team hulls and paint stay a workshop-only thing.

Shipped under this default (G5), with one change. The trim paints the wheel hubs rather than a stripe on the weapons: every part is one material and its second tone is a brightness multiplier baked into the geometry, so a stripe would need a second hue the material cannot carry, and hubs are the surface a real team livery paints anyway. Weapons stay bare steel. An unpainted bot (every stock fighter) keeps the team colour on its hull, and the team ring shows under every bot in every fight.

2. The catalog grows as tiers of the parts that exist, sold at tier-scaled prices

The decision. Nuts and Bolts' breadth came from a legible tier ladder (Standard, Heavy, Super) across a small set of part families, not from hundreds of unrelated parts. The catalog slice adds tiers to the families the game already has (wheels, plates, structural blocks, spikes and blades) plus a few missing silhouettes (a corner block, a wedge block, a pole and a skid). Every new part is additive data: colliders are new, no existing collider moves, so SIM_VERSION does not change and no replay is invalidated. New parts are sold in the shop at prices scaled by tier.

Why it matters. More parts means more things to buy with vibes, which changes how far a mining trip goes. It also interacts with the merge-level mechanic (question 3).

Recommended default: ship the tiers and price them so a tier-two part costs about the same as two tier-one copies (which is what a merge to level two costs today), so the two progression paths stay comparable. If you want the economy left alone, the new parts can ship as discoverable-only (mine finds) instead of shop stock.

3. Merge levels stay; tiers are separate parts

The finding. The 2026-08-12 tinkerer pass logged F-230, which says the merge-level mechanic (Lv 1 to 3 by consuming duplicate copies) is an idle-game mechanic bolted onto a machine shop, and proposes materials instead. Nuts and Bolts' answer to the same problem is distinct tiered parts. Doing both at once would give the player two overlapping upgrade ladders.

Recommended default: keep merge levels exactly as shipped (they are player-visible and inventory-backed) and add tiers as separate parts. F-230 stays open. If you would rather retire merge levels in favour of tiers, that is a migration slice with a durable marker (existing designs carry merge levels in saved JSON) and should be its own decision.

4. First visit: a blueprint on the bench, not a bare core

The decision. The strongest Nuts and Bolts lesson is that a blank bench intimidates. The onboarding slice makes a first-ever workshop visit open with the Cube Rammer blueprint already loaded and one wheel missing, with the empty axle glowing and a single coach line ("Drag the wheel onto the glowing mount"). Returning players see their last design as before. The starter design constant does not change, so tests and the Reset button still produce a bare core.

Why it matters. A first-time player who has not mined yet owns no parts. The bench lets them build with unowned parts (inventory is only enforced at match resolve), so the guided first drag works, but their first test fight against a stock bot will refuse to verify on the server until they own the parts. The local test fight still runs.

Recommended default: ship the guided first build as described, and make the first-visit coach line end by pointing at the Shop tab. If you would rather new players start with a small parts gift (two wheels and a spike) the way the mine starts with a support gift, say so and it becomes a server slice with a compatibility marker.

Shipped under this default (G6). One bounded exception was needed: the owned-out dim rule (an unowned part renders grey and cannot be dragged) would have stopped a brand-new player from placing the guide's wheel, so the guide's own wheel stays grabbable during its first step. Every other part keeps the rule. The guide runs once per browser (a localStorage flag, like the bunker tutorial), Skip ends it, the Garage can replay it, and opening a shared link retires it because a shared bot is its own first build.

Findings you should see, no answer strictly required

5. The nightly Full E2E has been red for sixteen consecutive nights, and one of those failures was a real regression

The finding. Every completed scheduled run from 2026-08-17 to 2026-09-01 concluded failure. On the current tip (cd9721c3, thirteen nights) a stable core of ten shards fails every night (6, 7, 8, 9, 12, 17, 20, 21, 22, 26) with four more drifting in and out (5, 10, 11, 25). The pre-#329 tip (7993ca5b) failed a near-identical core, so most of it is the standing software-render family from Q-035, which you chose to leave in place on 2026-07-30.

The regression. Shard 26 is new since #329. The menu copy cut removed the sentence "Safari does not let websites open that sheet automatically." from the Home Screen prompt, and E2E-RELEASE-NOTIFICATIONS-0008 still asserted it. That test fails deterministically on a hardware renderer too. It is fixed in this session's first PR by asserting the copy that shipped. Every other sampled nightly failure passed locally on hardware GL, which is the signature of the software-render family, not of a product defect.

Why it still matters. The push gate runs only the critical functional subset, so a copy change that breaks a non-critical spec is invisible until the nightly, and the nightly is already red, so nobody sees it. This is exactly the hidden-regression cost Q-035 accepted. No change to your decision is assumed; this is the first concrete instance of the cost, on the record.

6. Two watched dependencies had new releases, one of them a security fix

The finding. The Dependency Upgrade Gate fired twice at session start: next 16.3.4 over the pinned 16.3.1, and @react-three/fiber 9.7.0 over 9.6.1. Next 16.3.3 carries two critical advisories (unauthenticated remote code execution on Windows-hosted servers, and in the image optimization API with AVIF files) and 16.3.4 re-enables AVIF optimization after that fix. Production runs on Vercel's Linux runtime and the app does not use the image optimizer, so exposure was low, but the pin should not sit on a version with a published critical advisory.

What I did. Per the plan, both bumps are their own PRs and land before the feature program: Next first (security), then fiber. Fiber 9.7.0 is a reconciler hardening release (child reordering, pierced-prop reset, host-prop updates, react-dom event priorities); the canvases are the surface to smoke, and the critical e2e gate exercises both.

7. The HTML dots CLI has no Windows build

The finding. dot-html ships darwin-arm64 and linux-x86_64 binaries only, and the installer wants Zig for a source build, which this machine does not have. The task backlog is mandatory (AGENTS.md), so this session runs the Linux binary through WSL Ubuntu behind a two-line wrapper at ~/.local/bin/dot-html. It reads and writes the same .dots/ files. If you would rather have a native build, installing Zig via winget is the one-time cost.

8. Release-note cadence for the program

The finding. The package version and src/lib/app-release-notes.ts were last moved by the elevator slice (0.1.294). The seven tinkerer-depth slices that followed (#316 to #322) shipped player-facing changes with no version bump and no release note, so players were never told about the bench, weight classes, or gearing.

Recommended default: each player-facing slice of this program bumps the patch version and adds a release note, and the release notice id moves with it, so the in-game notice reflects what actually shipped. The Rule 13 tip review runs with each bump. Say so if you would rather batch the notes into one entry per milestone.
