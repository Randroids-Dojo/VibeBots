Working Agreement

This file defines the process rules for implementation slices on VibeBots.

Branches

  • Start every slice from current main.
  • Branch names should be short and descriptive: feature/manual-shifting, fix/leaderboard-pagination, docs/update-coverage.
  • Never push directly to main.
  • Do not mix unrelated changes in one branch.
  • Claim before you build: push the branch and open a draft PR as the first act of the slice (see Pull Requests). Put the backlog id in the branch name when one exists (fix/f-240-deploy-tripwire).

Commits

  • Use short human commit messages.
  • Do not include AI attribution.
  • Keep commits focused. A PR may contain more than one commit when review fixes are added.

Pull Requests

Every PR must include:

  • Summary of user-facing and technical changes.
  • Verification commands run.
  • GDD, coverage, followup, or open-question updates.
  • Any known limitations or blocked checks.

Attribution preflight (F-211, Rule 4):

  • Before merge, run pnpm check:attribution (scans the origin/main..HEAD range, i.e. every commit between the merge base and the head; also the attribution gate of pnpm verify).
  • Supply the squash subject and body explicitly, never from defaults, and validate the prepared text with bash scripts/check-attribution.sh --message-file <path>. PR titles and bodies can be validated the same way.
  • After the squash lands, verify the published commit with bash scripts/check-attribution.sh --commit <main-sha>.
  • The scan covers metadata only. Author and committer identity are out of scope unless the user separately expands the policy.

Claiming (adopted 2026-09-02):

  • The draft PR is the claim. Open it before implementing, right after the first push of the branch, so two sessions cannot probe the same slice concurrently (the failure Cannonball-Vibe hit with two probes of one task on 2026-08-30).
  • Before claiming, check gh pr list --state open --search "<F-id or Q-id>" (search covers PR bodies) and git ls-remote origin 'refs/heads/*' for the id or slug. If another branch or PR already names the slice, pick different work.
  • The first line of the PR body is Claims: F-NNN (or the Q-id, or none plus a one-line scope). Tracker ids stay out of the title (Rule 4).

After the slice is built and verified:

  • Mark the PR ready and arm auto-merge: gh pr merge <number> --auto --squash --subject "<title>" --body-file <path>, with the squash text validated by the attribution preflight first. Then start the next slice; do not wait for the merge, the preview deploy, or any bot.
  • No human or service review gates a merge. CodeRabbit is retired (.coderabbit.yaml disables automatic reviews while the app remains installed) and the settled-wait rule is gone with it. Review happens after merge, in docs/MAINLINE_REVIEW_LOG.html.
  • If a human leaves comments on your open PR, read flat comments, reviews, and threaded inline comments; fix what is valid, reply when the context would help future readers, resolve threads when fixed, and re-arm auto-merge if the push dropped it.
  • While the repository does not yet allow auto-merge (Q-038), merge yourself as soon as the required gate is green, with the same validated squash text.

Verification

Canonical local verifier (F-189):

  • The canonical command is pnpm verify (equivalently bash scripts/verify-local.sh; add --build for runtime-affecting slices). It runs the dash check, git diff --check (worktree and index), sim purity, the AGENTS link audit, the attribution scan, the followup-ledger validator, full lint, typecheck, and the unit suite as direct subprocesses, recording each gate's own exit status before any output is summarized. A promised gate whose script or prerequisite is missing is reported NOT-RUN, never silently omitted.
  • Never run a verification gate through a terminal pipeline whose final formatter can mask the gate's status (tsc | tail, biome check | tail -1, vitest | head). If concise output is needed, redirect to a file, save the exit status, then read the file. The verifier does this for every gate.
  • This applies to ANY command whose success is being relied on, not only the named gates. Setup and build commands count. A 2026-07-30 session ran pnpm install --frozen-lockfile 2>&1 | tail -25, read the pipeline's exit status (which came from tail, always 0) as success, and proceeded on an install that had actually aborted with a 403 (F-217). The failure was only caught later, from log text rather than from a status. Redirect and echo the command's own $? whenever the answer to "did that work?" determines what you do next.
  • A gate whose tooling is unavailable is reported NOT-RUN and the verifier exits nonzero. Missing tooling and skipped gates are never green evidence.
  • The verifier's own regression fixtures run with pnpm verify:selftest; they cover masked-failure, in-gate pipeline, multiple-failure, signal, missing-tool, empty-output, and all-green cases and need no installed dependencies.

Minimum for docs-only changes:

  • Dash check (U+2014 em-dash and U+2013 en-dash): grep -rnP '[\x{2014}\x{2013}]' . --exclude-dir=.git --exclude-dir=node_modules --exclude-dir=.next (must return nothing).
  • git diff --check.
  • Project-specific type-check command.

Minimum for code changes:

  • Dash checks.
  • git diff --check.
  • Type-check.
  • Relevant unit tests.
  • Full test suite when shared logic, storage, schemas, or core systems are touched.
  • Build command before opening or merging PRs that affect runtime code.
  • Critical smoke test (Playwright or equivalent) when UI routes, API routes, routing, or core flows are touched.
  • Full smoke test when shared UI shell behavior, cross-route storage state, release-note infrastructure, Playwright harness behavior, or another broad surface changes.

CI policy:

  • The push and PR gate is parallel CI: quality, type-check, unit tests, build, and sharded critical E2E.
  • The full Playwright smoke suite runs on schedule and manual dispatch. It is not required for every push unless the touched surface warrants it.
  • Older CI runs on the same branch or pull request are cancelled when a newer run starts.
  • When origin/main advances during closeout, verify whether the pushed commit is an ancestor of the new remote tip. If it is, follow the newest tip's checks and stop waiting on superseded runs.
  • The detailed policy lives in docs/CI_WORKFLOW.html.

Canvas text and atlas safety:

  • Normal DOM text is the preferred path for exact labels, counts, menus, dialogs, and HUD copy.
  • Do not add runtime 3D text renderers such as @react-three/drei Text or troika text inside the mine canvas without explicit approval. Mobile renderer fallback paths have shown failed glyph atlas quads as white squares.
  • For in-world mine labels, prefer mesh markers, icons, controlled sprite atlases, or DOM overlays anchored outside the canvas. If exact in-canvas text is unavoidable, add a mobile or narrow-viewport smoke test that samples canvas pixels for white-card artifacts.
  • When debugging a white square that follows the player, inspect in-scene text, sprite, and texture atlas paths before changing lights or materials.

Window dismissal rule:

  • Every new alert window, modal dialog, blocking prompt, or floating gameplay panel must be dismissible by clicking or tapping outside its visual bounds unless it is a destructive confirmation already inside a larger dismissible window.
  • Every new alert window, modal dialog, blocking prompt, or floating gameplay panel must also close on Escape and gamepad cancel/back.
  • Focused UI smoke coverage should exercise at least one pointer-outside dismissal path and one keyboard or gamepad dismissal path for new window patterns.

Versioned game-tip hygiene:

  • Every package version bump or app release-note update must include a review of the mine surface tip rotation in src/components/mine-panel.tsx.
  • Update, add, or remove tips when the release changes player-facing mine mechanics, economy, controls, upgrades, hazards, shops, or recovery rules.
  • Keep tips short, actionable, and current. They are not patch notes, tutorials, or a dumping ground for every feature.
  • Record the tip review in the progress-log verification or assumptions for the slice, including when no tip changes were needed.

Protected production verification:

  • Production Vercel URLs may show a Vercel login or security checkpoint before the app in unauthenticated automation. That is a platform gate, not a VibeBots UI state.
  • Do not run the standard Playwright suite against production with PLAYWRIGHT_BASE_URL. The standard suite uses a fresh browser context and can spend the whole run testing Vercel protection instead of the app.
  • Use local next start, preview CI, or the GitHub Actions critical smoke gate for Playwright evidence. For deploy readiness, use GitHub deployment status and Vercel CLI or API metadata tied to the commit sha.
  • Only run browser automation against production when the slice explicitly needs production playtest evidence, and then use an authenticated real browser context rather than a fresh headless context.

Minimum for dependency-upgrade slices (chore(deps): bump <dep> from <from> to <to>):

  • All of the above for code changes.
  • Read the upstream CHANGELOG between the pinned and target version BEFORE editing project code; document the breaking changes and migrations applied in the PR body.
  • Update docs/DEPENDENCY_LEDGER.html Currently pinned in the same PR.
  • Smoke test any feature that imports from the upgraded dep.
  • See docs/DEPENDENCY_LEDGER.html §Upgrade procedure for the full step list.

Never mark work complete with failing required verification.

Dependency Upgrade Gate

Run at every loop boundary that touches main:

  • At session start on fresh main, after the mainline health check and before picking the next slice.
  • Before marking a PR ready, in case a watched release landed while the slice was in flight.

Mechanism lives in docs/IMPLEMENTATION_PLAN.html §Dependency Upgrade Gate; the watched dep list and per-dep procedure live in docs/DEPENDENCY_LEDGER.html. Treat a new release as a non-optional signal: the upgrade is the next slice unless red main takes over.

Mainline Integration

Decision, 2026-09-02. Continuous mainline integration with post-merge adversarial review, adopted from the Cannonball-Vibe contract (that repo's ADR-0025 plus its task-claiming amendment). This section is the standing record; the loop in AGENTS.md Rule 5 and docs/IMPLEMENTATION_PLAN.html implements it.

Context

Delivery is single-owner and agent-executed. The pre-adoption gate stack (five required contexts plus a CodeRabbit settled-wait plus preview-deploy and production-smoke waits) cost every session a merge-babysitting tail and produced a documented pattern of review-service stalls resolved by admin override: PR #328 merged with an override after CodeRabbit's changes-requested state never flipped, and PR #330 hit a code_scanning ruleset rule that a docs-only PR can never satisfy. Development should continue without waiting on feedback outside the human boundaries in Rule 6, with breakage detected and repaired by agents.

Decision

  • Integration is PR-only and merges exclusively through auto-merge on green: squash only, zero required approvals, no pre-merge human or service review. CodeRabbit is retired.
  • The only required merge contexts are the five parallel CI jobs: Quality, Typecheck, Unit Tests, Build, and the two Critical E2E shards. Preview Smoke, Functional Shadow, and the render tier stay advisory.
  • The nightly Full E2E matrix, the pinned browser runtime build, and the production deploy become post-merge tripwires. The Mainline health workflow (.github/workflows/mainline-health.yml) watches the CI and Browser Runtime workflows on main and maintains one canonical open issue labeled red-main while any watched signal is red. Production deploy status is checked at session start until the watcher covers it (F-240).
  • Fix-forward only: never revert, never force-push, never bypass-merge to land work. A red main preempts all new slice selection; repair lands as new commits through the same PR flow. Administrator bypass is reserved for governance operations the owner performs personally.
  • A slice is claimed by a draft PR before implementation, so concurrent sessions cannot duplicate work.
  • Post-merge adversarial review replaces pre-merge review: mainline commits are reviewed from the cursor recorded in docs/MAINLINE_REVIEW_LOG.html, and actionable findings are filed as followups or open questions, never as merge blocks.
  • Rule 6 human boundaries are unchanged. The owner-side ruleset and repository setting changes that make auto-merge possible are recorded as Q-038 and executed by the owner, not by an agent.

Consequences

  • Integration no longer waits on review latency or deploy latency; agents arm auto-merge and move to the next slice.
  • There is a bounded window in which unreviewed or tripwire-failing code is on main; the red-main flow and fix-forward law are the accepted repair mechanism.
  • There is no merge queue and no strict up-to-date rule, so two independently green PRs can merge into a combined state never tested together; the push run on main plus the tripwire detect it.
  • Watched workflow name: fields are load-bearing for the watcher's workflow_run filter; renaming CI or Browser Runtime silently detaches it.
  • Ledger closeout happens in the slice's own diff, before the merge, because the merging session may never observe the merge.

Rejected alternatives

  • Direct push to main: loses the PR unit that required status checks and the ledgers key off, for negligible throughput over auto-merge.
  • Keep the bot settled-wait as advisory: retains an integration with a documented stall history that no longer gates anything.
  • Revert-first red-main policy: discards in-flight intent; fix-forward keeps diagnosis and repair in one continuous flow.
  • Make the Full E2E matrix a required PR check: serializes every merge on a thirty-two shard, 35-minute matrix whose known flakes would hold unrelated PRs.

Merge And Deploy

  • Merge only through PRs, only through auto-merge on the required parallel gate (see Mainline Integration).
  • Do not wait for the merge, the preview deploy, or a bot review after arming auto-merge. Start the next slice.
  • The next session start checks gh issue list --label red-main --state open and the production deployment status for the origin/main head. Red main is that session's slice.
  • Verify production deploy status and aliases through GitHub deployment status plus Vercel CLI or API metadata, keyed by commit sha.
  • Do not use unauthenticated HTTP checks or fresh headless Playwright as the default production smoke path on protected Vercel deployments. Use local or CI Playwright for app behavior, and reserve authenticated real-browser production playtests for slices that explicitly need them.
  • Never revert, force-push, or bypass-merge to land work or to clear a red main.

Clarifications

Ask only when ambiguity is expensive or risky. When a simple consistent default is available, choose it, record the assumption in docs/OPEN_QUESTIONS.html with a Recommended default entry, and continue.

Risk Gates

Always stop for explicit user approval before:

  • Force pushes.
  • Hard resets.
  • Recursive deletes.
  • Dropping data store keys or deleting remote data.
  • Deleting branches other than branches created for the current completed PR.
  • Modifying CI/CD configuration.
  • Uploading content to third-party services outside the existing PR and deploy flow.
  • Handling secrets.

Compatibility Migrations

Any existing-player cleanup or one-time compatibility grant must have a durable marker column. Add player-level markers to PLAYER_COMPATIBILITY_MARKERS in src/server/db.ts, add the matching lazy schema column, and gate the cleanup with WHERE marker IS NULL so temporary forgiveness cannot become a permanent rule.
