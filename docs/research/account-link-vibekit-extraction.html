Account Link VibeKit Extraction Contract

Status: staged after the VibeBots account-sync spike. The current reusable shape lives in src/lib/account-link-core.ts, outside the VibeBots server adapter.

Why Extract

VibeBots needs optional Google sign-in now, but the durable part is not Clerk. The reusable part is the claim policy: normalize a provider identity, check whether that account already owns a save, claim an unlinked guest save, and return a non-destructive conflict when needed.

Package Boundary

The VibeKit package should export only provider-neutral account-link primitives. It should not import Clerk, Next.js, Neon, Vercel, React, cookies, request objects, or a specific database driver.

export interface AccountIdentity {
  provider: string;
  subject: string;
  email?: string;
}

export type AccountClaimResult =
  | { status: "claimed"; playerId: string }
  | { status: "already-linked"; playerId: string }
  | { status: "conflict"; playerId: string }
  | { status: "invalid-identity" }
  | { status: "player-not-found" };

export type AccountLinkAttempt =
  | { status: "claimed"; playerId: string }
  | { status: "already-linked"; playerId: string }
  | { status: "linked-to-other-account"; playerId: string }
  | { status: "invalid-identity" }
  | { status: "player-not-found" };

export type AccountLoadResult<Session> =
  | { status: "loaded"; playerId: string; session: Session }
  | { status: "invalid-identity" }
  | { status: "not-found" };

export type AccountLinkedSaveStatus =
  | { status: "signed-in-unlinked" }
  | { status: "cloud-loaded"; playerId: string }
  | { status: "conflict"; playerId: string };

export interface AccountLinkStore {
  findLinkedPlayer(identity: AccountIdentity): Promise<string | null>;
  claimUnlinkedPlayer(identity: AccountIdentity, playerId: string): Promise<AccountLinkAttempt>;
}

export interface AccountSessionWriter<Session> {
  writeActivePlayer(playerId: string): Promise<Session>;
}

The package should also export normalizeAccountIdentity, claimAccountPlayer, loadLinkedAccountPlayer, and accountLinkedSaveStatus.

normalizeAccountIdentity should keep provider identities stable before an app-owned store sees them: provider names are lower-case ASCII tokens up to 64 characters, subjects are trimmed non-empty non-control strings up to 256 characters, and optional email is trimmed non-control display metadata capped at 320 characters. Provider subject remains the authority; email must never be used as the account-link key.

invalid-identity is distinct from player-not-found. Malformed provider identities or app-unsupported provider identities must not be reported as missing saves, because another app reusing the claim helper needs to distinguish account input rejection from game-row lookup failure.

loadLinkedAccountPlayer is the reusable cross-device load primitive. It normalizes the account identity, finds the linked player through the app-owned store, and calls an injected AccountSessionWriter to make that player active. VibeBots passes its save-slot cookie writer; another app can pass its own session mechanism without sharing cookies or tables.

accountLinkedSaveStatus is the reusable status classifier. It reports an unlinked signed-in account, a loaded cloud save when the active player already matches the linked player, or a non-destructive conflict when the linked player differs from the active player. Apps still decide when to write a session, such as VibeBots' same-origin fresh-browser auto-load rule.

The OAuth handoff URL contract is now staged as src/lib/account-handoff-contract.ts. It owns bounded handoff ids and local return-path sanitization for server storage, browser response parsing, callback posting, and redirect construction without importing Clerk, Next.js, React, cookies, requests, or storage. safeLocalAccountReturnTo is the provider-neutral helper: an app supplies the fallback path and route allowlist. The helper accepts only local forward-slash paths, rejects protocol-relative URLs, backslashes, ASCII control characters, and overlong paths, then applies the app-owned allowlist. safeAccountReturnTo is the VibeBots wrapper that allowlists only the mine route for account callbacks. The browser account API parser also runs handoff start returnTo values through this wrapper before the Account dialog builds a Clerk redirect.

Provider readiness status can also be extracted later as a small provider-neutral contract if another project needs setup gates. The VibeBots staging module is src/lib/account-provider-status.ts, backed by src/lib/account-provider-status-codes.json; together they own the known Clerk readiness issue codes and shared provider-status type without importing Clerk, Next.js, React, cookies, requests, or storage. App routes remain app-owned: VibeBots requires one local /sign-in sign-in-or-up route, an installed @clerk/nextjs dependency before the SDK-backed provider can report ready, Clerk key prefixes that match their public or secret role, rejects a separate public sign-up URL, requires /mine?account=1 for both sign-in and sign-up fallback redirects, rejects public and server sign-in or sign-up force redirect env vars because they would bypass the app-owned handoff token, and rejects public and server deprecated after-redirect env vars because the app uses Clerk fallback redirects for new setup. Another app should provide its own local paths, dependency policy, key-shape policy, and redirect policy.

The provider-session resolver stays app-owned. VibeBots stages the Clerk-specific adapter in src/server/clerk-account-session.ts: it accepts injected Clerk-like server helpers, only maps string user ids and string email metadata, verifies auth and user helpers agree on the same user id, and treats helper errors as signed out. VibeKit should not absorb that Clerk helper shape; it should only receive a normalized AccountIdentity from the app-owned resolver.

The Google identity-scope contract is also staged for VibeKit reuse. The reusable package can export ACCOUNT_GOOGLE_IDENTITY_SCOPES, accountGoogleIdentityScopeString, accountGoogleScopeListFromString, accountGoogleScopeStringIsIdentityOnly, isAccountGoogleIdentityScope, and accountGoogleScopesAreIdentityOnly from a provider-neutral module backed by the same minimal JSON data shape as src/lib/account-google-scopes.json. The package should keep this contract limited to openid, email, and profile; app-specific setup tools can require operators to declare dashboard scopes and validate that declaration against the shared helper.

App-Owned Pieces

  • Provider session resolver. In VibeBots, Clerk will produce { provider: "clerk", subject: userId, email }.
  • Provider-specific readiness evaluation. VibeBots decides which Clerk env keys, key-prefix checks, local sign-in route, sign-up route exclusions, local sign-in plus sign-up account fallback routes, public and server force redirect exclusions, and public and server deprecated after-redirect exclusions are required before exposing Google sign-in.
  • Storage adapter. VibeBots currently adapts players.clerk_user_id in src/server/account-linking.ts; another app can use a generic account_links table.
  • Cookie or session-slot write. VibeBots owns setActiveSaveSlotPlayer.
  • HTTP routes, OAuth handoff token storage, and UI state.
  • Telemetry and alerting policy.

Extraction Steps

  1. Copy src/lib/account-link-core.ts into VibeKit under a server-safe export path.
  2. Port src/lib/account-link-core.test.ts, including the purity guard that forbids app, provider, and framework imports.
  3. Release VibeKit with those exports, then update VibeBots to import them from @randroids-dojo/vibekit.
  4. Keep src/server/account-linking.ts in VibeBots as the Clerk-column adapter until a generic account-links table is worth adding.
  5. Do not extract the handoff table yet. It is more app-specific because it depends on browser embedding, cookie partitioning, and active save-slot semantics. The shared URL safety helper can remain a staging contract until another project proves reuse.
  6. If extracting the handoff URL helper, move safeLocalAccountReturnTo and safeAccountHandoffId into VibeKit while keeping each app's callback route allowlist local. Another project should not be forced to use VibeBots' mine route.
  7. Extract the Google identity-scope helper before any second app wires Google sign-in, so each project can share the same no-Drive, no-Gmail, no-Contacts consent rule while keeping its provider SDK and dashboard checks app-owned.

Acceptance Criteria

  • VibeKit exports no Clerk, Next.js, Neon, Vercel, React, cookie, or request types for account linking.
  • VibeBots tests still prove claim success, idempotence, account-conflict, player-conflict, invalid-identity, and missing-player behavior.
  • VibeBots tests still prove linked account load success, not-found, invalid-identity, and app-owned session writing through loadLinkedAccountPlayer.
  • VibeBots tests still prove account status classification for unlinked, loaded, conflict, and no-active-player states through accountLinkedSaveStatus.
  • Any extracted provider-status helper keeps a purity guard like src/lib/account-provider-status.test.ts, proving it imports no provider, framework, storage, app, state, or component modules.
  • Any extracted Google scope helper keeps a data-shape guard like src/lib/account-google-scopes.test.ts, proving the shared data exposes only the identity scope list and rejects Drive, Gmail, Contacts, duplicates, missing scopes, and other non-identity scopes.
  • VibeBots can switch from the local core import to the VibeKit export without changing account route responses.
  • Another project can provide its own AccountLinkStore and reuse claimAccountPlayer without sharing VibeBots tables or cookies.
