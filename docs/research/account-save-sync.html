Multi-Device Save Sync

Status: research complete, implementation planned as three slices (dots VibeBots-sync-freshness-*, VibeBots-sync-stale-checkpoint-*, VibeBots-sync-save-push-*).

Account sync (REQ-042) lets one Google-backed save load on several devices. This pass designs how those devices stay coherent while playing, after a live two-device playtest on 2026-07-05 showed how easily they drift.

Problem: the reproduced two-device conflict

  1. Sign into the same account on devices A and B; both load the same cloud save (same playerId).
  2. Device A mines a trip and returns to the surface. Cash-out advances mine_worlds.trip_count and rewrites the world diff.
  3. Device B, still holding the old world (old seed plus tripIndex), mines a full trip.
  4. Device B's cash-out is rejected: the server's compare-and-set on trip_count returns trip_already_cashed_out.

The server state is never corrupted. The cost is entirely player-facing: device B plays a doomed trip with no warning and loses the run to a raw error message.

Current state (verified 2026-07-06)

  • src/app/api/mine/bank/route.ts validates submitted seed against mine_worlds.seed (wrong_mine_seed) and tripIndex against trip_count (trip_already_cashed_out), and the credit UPDATE is guarded with AND trip_count = tripIndex. Server-side protection is already correct.
  • mine_trip_checkpoints is one row per player and the PUT in src/app/api/account/trip/route.ts is a blind upsert: a stale device silently overwrites a fresh device's in-flight trip checkpoint.
  • The client (src/state/mine-store.ts) holds exactly the freshness token it needs: its current seed and tripIndex. It never revalidates them after the initial world load.
  • Web Push already exists per player (push_subscriptions keyed by player_id plus endpoint; VAPID env; public/sw.js). Cloud-linked devices share one playerId, so "this account's other devices" is already expressible. Constraint: browsers require every push to show a visible notification, so push cannot be a silent data channel.
  • Deterministic replay means two divergent trips on one world cannot be merged. Whichever banks first wins; the other trip is unsalvageable by design. The goal is therefore to make the losing trip short, not to recover it.

Design: four layers

Layer 1: freshness checks at the moments that matter

  • Expose a cheap world-version probe returning { seed, tripCount } for the current player (either a dedicated GET /api/mine/world/version or an extra field on an existing read). One indexed primary-key SELECT.
  • Cloud-loaded clients revalidate on visibilitychange, focus, and pageshow, and before the first move of each new trip.
  • Compare against local seed/tripIndex. A mismatch means another device advanced the save.
  • In the reproduced scenario, device B learns it is stale when it is picked back up, before mining anything.

Layer 2: one consistent conflict flow

  • Every staleness discovery (probe mismatch, stale-checkpoint rejection, bank failure) funnels into one rule.
  • No local moves yet: resync silently (reload world, gear, account status). Nothing is lost, no prompt.
  • Local moves exist: modal dialog "Your cloud save advanced on another device." Primary action Sync now (discards this run's progress), secondary Keep playing (run is marked doomed; banking will be refused and the modal returns at cash-out). Honest copy: the run cannot be merged.
  • The existing raw trip_already_cashed_out cash-out error upgrades into this same flow instead of a text error.
  • Modal follows Rule 10: z-index above fixed surfaces, keyboard activation preserved, focus handled like the account dialog.

Layer 3: reject stale trip checkpoints server-side

  • The trip checkpoint payload already carries tripIndex. The PUT compares it to mine_worlds.trip_count and returns 409 stale_trip_checkpoint on mismatch.
  • Stops a stale device from overwriting a fresh device's checkpoint, and doubles as an early conflict tripwire because checkpoints are written at every account interaction.
  • Wants the stable account error-code contract (followup F-068) so the client branches on code, not prose.

Layer 4: save-sync push for backgrounded devices

  • On save-mutating events (successful bank, claim), send Web Push to the player's other subscriptions: tag vibebots-save-sync (repeats replace, never stack), body "Your save advanced on another device. Open to sync.", URL /mine.
  • Suppress the originating device: the client sends a hash of its own subscription endpoint with the mutating request; the server skips that subscription.
  • Rate limit per endpoint (skip if the last save-sync push was within a couple of minutes).
  • Stays opt-in behind the existing notifications toggle; covers only the closed or backgrounded app. The open app is covered by layer 1, which needs no permission and cannot spam.
  • A BroadcastChannel ping covers same-browser multi-tab for free.

Decisions

  • Last bank wins; no trip merging. Deterministic replay of divergent moves over one world is unresolvable, so the design shortens the losing trip instead of recovering it.
  • Always prompt before dropping moves; never auto-discard player progress silently.
  • Polling loops are avoided; revalidation happens on lifecycle events plus trip start.
  • Push is a wake-up channel, not the sync mechanism. In-app freshness checks are the mechanism.

Implementation slices

  1. Slice A (layers 1 + 2): version probe, lifecycle plus trip-start revalidation, conflict modal, cash-out error upgrade. Store unit tests for conflict transitions plus an e2e that replays the two-device repro with mocked routes.
  2. Slice B (layer 3): stale-checkpoint 409 plus client handling. Route tests and store tests.
  3. Slice C (layer 4): save-sync push with tag, origin suppression, rate limit, sw.js handling, BroadcastChannel. Server unit tests plus notification route tests.
