Account Sync With Google Sign-In

Status: design complete, server boundary and mine account UI implemented, Clerk development SDK wiring landed, production provider setup and real Google OAuth verification pending.

This research pass designs the optional account layer for VibeBots. The player must still be able to start with no account, keep playing with the current guest save, and later attach that save to Google sign-in so the same progress loads on another machine.

Goals

  • Keep first play account-free. No sign-in wall, no onboarding form, and no email prompt before the mine is useful.
  • Let a guest player intentionally save the current active slot to a Google-backed account.
  • Load the claimed save on another browser after Google sign-in.
  • Keep the implementation simple enough for a solo project and cheap until real returning usage exists.
  • Integrate cleanly with Vercel and the existing dedicated Neon database.
  • Put reusable account-linking primitives behind a small VibeKit-shaped boundary.

Recommended Architecture

  1. Keep the signed guest cookie as the base identity. Every new player still starts with a guest slot and can play immediately.
  2. Add Clerk as an optional session provider. Do not protect gameplay routes globally. Public routes still work for guest players. Only report providerReady once the server resolver is wired, not merely when public Clerk env vars exist.
  3. Resolve account identity at the server boundary with a provider-neutral value: { provider: "clerk", subject: clerkUserId, email }. Use clerkAccountIdentityResolver so Clerk auth state and profile shape stay isolated from the reusable account-linking core.
  4. Claim the current active player row by writing players.clerk_user_id only after the player clicks "Save to account" and the server confirms there is no conflicting existing cloud save.
  5. When a signed-in player has a claimed row, rewrite the active slot in vb_player to that row id so all existing routes keep using the same player-id contract.
  6. Keep device-local slots separate from account slots. The first implementation claims only the active slot. Multi-slot cloud sync can be a later explicit feature.
  7. Handle iframe embedding with a top-level auth handoff. The OAuth flow runs outside the iframe, then returns a one-time claim code to the embedded game so the partitioned vb_player cookie is set inside the right storage partition.
  8. Require same-origin browser requests for account mutations. Claim, cloud-load, handoff start, and handoff finish all mutate cookie-backed account state and must reject cross-site browser POSTs before storage or account lookup.

Player Flow

  1. New player opens VibeBots and plays as a guest. The pause menu shows account state as "Guest save".
  2. The player clicks "Save to account". The client saves the current in-flight trip checkpoint, flushes any required cash-out or world reload state, then starts Google sign-in. If the checkpoint write fails, sign-in does not start and the guest save remains on this device.
  3. After Google returns, the server checks for an existing row with this provider subject.
  4. If none exists, the server claims the active guest player row and marks the menu as "Saved to Google".
  5. If a cloud row exists and it is the same active row, the client simply refreshes account state.
  6. If a different cloud row exists, the client shows a non-destructive choice: "Use Google save" or "Keep this device save". The first implementation must not merge or overwrite automatically.
  7. On another machine, signing in finds the claimed row and writes it into the active slot cookie when there is no local active player. The player continues from the cloud save without a manual conflict prompt.

Conflict Policy

  • Never auto-merge two player rows. The current game stores many durable row-owned tables: mine world, wallet, gear, inventory, designs, bunker, raids, achievements, performance samples, feedback, notifications, match records, and balance events.
  • Never delete a guest row during sign-in. If a signed-in account already has a cloud save, the guest row remains in the device cookie until the player chooses an explicit replace or delete flow.
  • Use account identity only as a pointer to one player row. The player row remains the game authority.
  • Use a database uniqueness guard so one Google account cannot claim two player rows at the same time. If two claim requests race, the loser re-reads the linked account row and returns a normal conflict instead of failing open or throwing a generic server error.

Data Model

  • Keep players.clerk_user_id text for the first Clerk adapter.
  • Add a partial unique index: CREATE UNIQUE INDEX IF NOT EXISTS players_clerk_user_id_unique ON players (clerk_user_id) WHERE clerk_user_id IS NOT NULL.
  • For VibeKit reuse, prefer a future generic table: account_links(provider text, subject text, player_id uuid, linked_at timestamptz, primary key(provider, subject)). VibeBots can start with clerk_user_id because the column already exists, then migrate behind the same adapter interface later.
  • Account-linking telemetry logs safe hashes only: no emails, no handoff tokens, and no Google profile payloads. Landed 2026-07-04 through the account.link monitoring component. Handoff finish also rejects malformed or oversized handoff ids before storage lookup.

API Shape

  • GET /api/account/status: returns { mode: "guest" | "signed_in" | "cloud_loaded" | "conflict", providerReady, providerStatus, activeSlot, account, currentSave, accountSave } with safe summaries only. Guest mode includes the current active save summary when a player row exists, so the Account dialog can show what will be attached before sign-in. Browser parsing now rejects account-owned modes when the account field is missing, and rejects cloud-loaded or conflict modes without an existing account save. providerStatus is the typed provider readiness contract; the current no-SDK resolver reports Clerk as not ready with sdk_not_wired and sdk_dependency_missing, and includes a non-secret issues checklist for missing setup pieces such as missing or malformed Clerk keys, an absent /sign-in route, a configured separate sign-up URL, missing sign-in and sign-up fallback routes back to /mine?account=1, configured public or server force redirects that would bypass the account handoff token, or configured public or server deprecated after-redirect env vars. accountProviderStatusFromConfig is the tested helper the approved SDK slice should use to flip readiness only after the resolver, @clerk/nextjs dependency, Clerk keys with expected prefixes, public sign-in route, unset public sign-up URL, account-dialog fallback routes, unset public and server force redirect URLs, and unset public and server deprecated after-redirect URLs are configured. Status passes the provider and status into currentReadyAccountIdentity, so partial Clerk setup stays in guest mode and cannot attach a cloud save even if a test or future resolver can produce an identity. If a signed-in account has a linked cloud save and the current browser has no active local player, a same-origin app status request writes that account player into the active save-slot cookie and reports cloud_loaded. Cross-site browser status reads never trigger that cookie-backed attach.
  • POST /api/account/claim: requires a signed-in account and a current guest player. Claims the active row or returns a conflict without mutating rows.
  • POST /api/account/load: requires a signed-in account with an existing claimed row. Writes that row to the active slot cookie for this browser partition.
  • GET /api/account/trip: requires a signed-in account with a linked player row and returns the account mine trip checkpoint, or null when none exists. The client stores this locally before loading the cloud world so the existing resume guard can replay only matching checkpoints.
  • PUT /api/account/trip: requires a current guest player and same-origin browser request. Stores the current browser-local mine trip checkpoint for the active player row before sign-in start or account claim.
  • POST /api/account/handoff/start: creates a short-lived state value before opening top-level sign-in from an embedded context. Landed 2026-07-04 with a database-backed token that stores the current guest player row and a sanitized local return path. The return-path sanitizer and handoff id validator now live in the shared src/lib/account-handoff-contract.ts module used by both server and browser code. Handoff creation prunes expired or consumed rows first, clears any still-pending handoff rows for the same player, and the table has an expiry index so this remains cheap without a scheduled cleanup job.
  • POST /api/account/handoff/finish: consumes the one-time state after sign-in and sets the embedded partition's player cookie. Landed 2026-07-04 with the same non-destructive conflict policy as /api/account/claim.
  • All account mutation routes require same-origin browser requests through sameOriginMutationRequired. Cross-site claim, load, handoff start, handoff finish, and trip checkpoint write attempts receive 403 before storage or identity lookup.
  • All account route JSON uses Cache-Control: no-store. Account status, claim, load, handoff, and same-origin rejection responses are per-player and must not be reused across browser partitions, guests, or signed-in Google sessions.
  • Handoff start also requires accountProviderReady(). Until the Clerk resolver is approved and wired, the server refuses to mint sign-in handoff tokens and account status reports providerStatus.ready: false.

VibeKit Abstraction

VibeKit should not force Clerk, Neon Auth, or Better Auth as a hard dependency. It should expose account-linking primitives and let each app provide the provider resolver. VibeBots now has this shape in src/lib/account-link-core.ts: a provider-neutral claim coordinator plus an app-owned store adapter. The current store adapter remains players.clerk_user_id in src/server/account-linking.ts. The core reports malformed or adapter-unsupported provider input as invalid-identity, separate from player-not-found, so reusable callers can distinguish account rejection from missing game saves.

export interface AccountIdentity {
  provider: string;
  subject: string;
  email?: string;
}

export interface AccountLinkStore {
  findLinkedPlayer(identity: AccountIdentity): Promise<string | null>;
  claimUnlinkedPlayer(identity: AccountIdentity, playerId: string): Promise<AccountLinkAttempt>;
}

export interface GuestSessionStore {
  writeActivePlayer(playerId: string): Promise<void>;
}

The shared core now also exposes loadLinkedAccountPlayer, which resolves a claimed account save and calls an injected session writer. accountLinkedSaveStatus classifies unlinked, loaded, and conflict account states without touching cookies. VibeBots uses those helpers for explicit cloud-save loading and status responses while keeping save-slot cookies app-owned. Another project can implement the same contract with Better Auth, Neon Auth, or a custom provider without changing game save semantics.
