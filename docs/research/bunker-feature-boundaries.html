Bunker Feature Boundaries

Boundary map for F-038. The goal is to make bunker work discoverable without collapsing sim, server, API, store, panel, and canvas ownership into one broad feature module.

Summary

The bunker feature crosses the mine loop, but each layer has a narrow job. Future bunker slices should start by identifying which owner below has authority for the change, then touch the smallest adjacent boundary needed for tests and UI wiring.

Owners

Pure sim rules
src/sim/bunker.ts owns base-part catalog data, claim geometry, placement and removal rules, inventory spend and refund rules, raid pathing, Clanker raid resolution, raid wear, XP pickup snapshots, and player-level math. It must stay pure and deterministic.
Mine sim handoff
src/state/mine-store.ts owns pending unbanked bunker edits during a live mine trip. It decides when a claimed bunker is still local-only and when cash-out can persist that claim through /api/mine/bank.
Server persistence and policy
src/server/bunker.ts owns database reads and writes, starter base-part provisioning, legacy active-raid normalization, wallet checks, raid cooldowns, reward writes, achievement hooks, and balance telemetry. Server helpers return typed operation results instead of HTTP responses.
API route boundary
src/app/api/bunker/** owns request parsing, Zod validation, storage gating, player lookup, and HTTP response mapping through src/server/api-boundary.ts. Routes should stay thin and delegate policy to src/server/bunker.ts.
Shared wire types
src/lib/bunker-api-types.ts owns the bunker route view shape shared by server responses and client state. It should contain types only, with no fetch, database, React, or sim logic beyond type imports.
Client API facade
src/state/bunker-api-client.ts owns bunker route URLs, HTTP methods, JSON bodies, response parsing, network failures, and route error extraction for the client. It should not update Zustand state.
Zustand state
src/state/bunker-store.ts owns client-visible bunker status, loaded bunker state, inventory, active raid, player progress, last raid reward, user notes, and how successful or failed API results update those fields.
Mine panel controls
src/components/mine-panel.tsx and src/components/mine-bunker-control-panel.tsx own claim mode, builder panel visibility, selected base part, build mode, raid pickup retry timing, and button wiring into mine and bunker stores.
Mine canvas overlay
src/components/mine-canvas.tsx passes bunker props into src/components/mine-bunker-overlay.tsx. The overlay owns visual claim outlines, blocked-cell highlights, placed base-part visuals, Clanker paths, XP pickup visuals, hover targets, taps, and drag targets. It should not own server state or route calls.

Change Routing

  • Change base-part legality, raid outcome, XP math, or level math in the pure sim first, then update server and UI consumers.
  • Change persistence, starter grants, rewards, cooldowns, or legacy row normalization in server helpers and route tests.
  • Change HTTP request or response handling in the client API facade, with store tests proving state results stay compatible.
  • Change local pending-claim behavior in the mine store, because unbanked claims are part of the trip replay contract.
  • Change controls and copy in the panel components. Change rendered geometry, animation, and pointer hit behavior in the canvas overlay.

Guardrails

  • Do not move the full bunker feature into one folder until import churn creates a real problem.
  • Do not import React, Zustand, Next route handlers, server code, or database code into src/sim/bunker.ts.
  • Do not make API routes own bunker policy beyond validation and response mapping.
  • Do not make the client API facade mutate Zustand state.
  • Do not make the canvas overlay fetch or persist bunker data.
  • Use src/lib/bunker-api-types.ts for shared route shapes so server and client changes stay visible to TypeScript.
