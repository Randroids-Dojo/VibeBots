In-Game Performance Analyzer

Design for the opt-in deep performance telemetry system (extends REQ-041 and followup F-054). Written 2026-07-06 before the implementation slice.

Problem

The existing sampler (src/components/mine-performance-sampling.ts) records one 12-second frame-percentile summary per hour per player, mine surface only. It can tell us that a device is slow, but not why: it carries no scene composition, no GPU timing, no main-thread attribution, and no memory data. Diagnosing bottlenecks (lighting, model complexity, animations, particles, object churn) requires correlating frame cost with what the renderer was actually doing at that moment, on both desktop and mobile.

Prior art and platform capabilities

  • three.js renderer info: renderer.info.render (calls, triangles, points, lines) and renderer.info.memory (geometries, textures) are cheap per-frame counters on both the WebGPU and the WebGL2 backend. The mine canvas already publishes info.render.calls via canvas.dataset.drawCalls.
  • GPU frame timing: three's WebGPURenderer supports trackTimestamp: true at construction, which requests the timestamp-query feature and lets renderer.resolveTimestampsAsync(TimestampQuery.RENDER) return the measured GPU pass time in ms. This separates GPU-bound frames (shading, overdraw, shadow passes) from CPU-bound frames. It must be requested at renderer creation, so it activates on the canvas mount after the toggle is on.
  • Long Animation Frames (LoAF): PerformanceObserver with type long-animation-frame reports frames over 50 ms with script attribution (which source URL burned the time). Chromium only; the observer no-ops elsewhere. Best practice is to report only summaries and the top offenders, not every entry.
  • Long tasks: the longtask entry type is the wider-support fallback signal for main-thread stalls.
  • Event timing: the event entry type with a duration threshold approximates INP and catches input-to-paint stalls during play.
  • Memory: performance.memory.usedJSHeapSize (Chromium) plus three's geometry/texture counts give a churn signal (leaks, allocation storms) without precise-memory permissions.
  • GPU identity: WebGPU exposes GPUAdapter.info (vendor, architecture); WebGL2 exposes the unmasked renderer string through WEBGL_debug_renderer_info. Either one turns "some phones are slow" into "Mali-G57 is slow".

Design

Principles

  • Opt-in and honest: a Performance Telemetry toggle in the mine settings menu (aria-pressed, persisted in localStorage). Off by default; the passive hourly sampler stays as the always-on baseline.
  • Snapshot = metrics + scene state: every snapshot row carries both the frame-time distribution for its window and the renderer/scene composition during that window, so factor analysis (frame cost vs draw calls, triangles, lights, particles, memory) is a plain SQL/JS aggregation later.
  • Render-only observation: probes read renderer.info, traverse the scene at snapshot boundaries, and read the diagnostics the canvases already publish on canvas.dataset. Nothing touches src/sim or deterministic state.
  • Cheap when off, bounded when on: zero observers and zero rAF work while disabled. When enabled: one rAF delta collector, one scene traversal per snapshot (5 s), batched uploads (~20 s), capped payload sizes, flush on pagehide via keepalive.
  • Comparable across builds and devices: every row records app version and build, mine version, renderer backend, graphics tier, device class, and an A/B variant tag so fixes can be measured quantitatively.

Client architecture

  • src/lib/perf-analyzer-settings.ts: renderer-free setting storage (vibebots-perf-analyzer-v1), A/B variant storage (vibebots-perf-ab-variant, also settable with the ?perfVariant= query param), window overrides for tests.
  • src/lib/perf-trace.ts: pure snapshot/payload shaping: frame summaries (reuses summarizeFrameMetrics), stall counting, numeric clamping, payload caps. Unit-tested.
  • src/components/perf-probe.ts: a module-level probe registry. Each R3F canvas mounts a <PerfProbeBridge source="mine"> that registers a probe closure over { gl, scene }. A probe call (only at snapshot boundaries) returns renderer info, scene composition counts (meshes, instanced meshes and instances, lights by type, shadow casters, sprites, visible objects, unique materials and geometries), backend identity, and the allowlisted canvas.dataset diagnostics (particle count, rendered cell count, teeter/gas-wisp counts, time of day, camera depth/zoom, smoothed frame ms). The bridge also resolves GPU render-pass time about once per second when the WebGPU backend has timestamps enabled.
  • src/components/perf-telemetry.tsx: the page-level collector. While the toggle is on and the page is visible it runs a rAF frame-delta loop, LoAF/longtask/event observers, and every 5 s emits a snapshot (frame summary + probe + memory + main-thread summary), buffering and posting batches to POST /api/performance/trace. Mounted on mine, arena, workshop, and holodeck pages with their own source tags.
  • createWebGPU passes trackTimestamp when the analyzer is enabled at canvas creation, so GPU timings appear from the next canvas mount onward.

Storage (one dedicated Neon Postgres, Rule 11)

New append-only table player_perf_traces: one row per snapshot. Queryable factor columns (frame percentiles, GPU ms, draw calls, triangles, geometries, textures, mesh/instance/light/particle counts, JS heap MB, long-task and LoAF summaries, input-event summaries) plus a capped detail jsonb for the long tail (lights by type, LoAF top scripts, canvas diagnostics). Session identity (random per page load) groups snapshots; player id ties devices across sessions. Indexes on created_at, (source, created_at), and (p95_frame_ms, created_at).

Query path

GET /api/performance/insights aggregates recent traces server-side and returns anonymized rollups only (no player ids, no raw user agents): overview counts, segment breakdowns by source/renderer/tier/device class, factor buckets (avg p95 by draw-call, triangle, light, particle, and heap buckets), and the worst snapshots with their factor columns. This is the verification and triage surface for operators and agents; ad-hoc SQL against Neon stays available for deep dives.

A/B measurement plan

Every trace row records ab_variant (default null). To quantify a candidate fix: ship it behind a variant check (or as a build), assign variants via the query param or a randomized localStorage assignment in the fix's slice, then compare p95_frame_ms, gpu_frame_ms, and factor columns between variants (or between app builds) for the same renderer/tier segments in the insights endpoint. App build is always recorded, so before/after release comparisons work even without an explicit variant.

Bottleneck hypotheses to test with the data

  • Draw calls on phones: the mine budget lives and dies by draw calls on forced-WebGL2 devices; correlate p95 against draw_calls and rendered cell count per tier.
  • Shadow + IBL cost on high tier: compare GPU ms with shadows/postBloom on vs off (tier segments already encode this).
  • Particle bursts: dynamite/collapse moments spike particle_count; check whether p95 spikes track them.
  • Time-of-day lighting: surface scenes carry sun + hemisphere + ambient + IBL; underground scenes are lamp-driven. The timeOfDay/camera-depth diagnostics separate the two regimes.
  • Memory churn: heap growth across a session (same session_id, rising js_heap_mb) points at allocation leaks; geometry/texture count growth points at renderer-resource leaks.
  • Main-thread stalls vs GPU-bound frames: LoAF/longtask totals vs GPU ms decide whether to optimize scripts (React re-renders, store updates) or shading/geometry.

Privacy and volume

  • Opt-in only; the toggle copy says what is collected and where it goes.
  • No gameplay-economy data, no text input, no identifiers beyond the existing player cookie the API routes already use.
  • The public insights endpoint returns aggregates and factor columns only, never player ids or raw user agents.
  • Volume bound: 1 row / 5 s per opted-in player (~720 rows/hour worst case), batched into ~3 POSTs/minute. Zod caps batch size and string lengths server-side.

Root-cause drilldown (2026-07-07 slice)

The first real data run answered "is it slow" but not "why". A real phone session (Mali arm valhall, mine webgl2/low) showed a locked 60 fps steady state with an isolated 1.4 s frame, and the stored rows could not say whether that stall was script, GC, network, scene load, or an app switch. This slice closes that gap.

What each snapshot window now records

  • Network: a resource-timing rollup (request count, transfer KB, total and max duration) plus the top three slowest requests. Paths are same-origin pathnames with query strings stripped; cross-origin requests record the bare origin; the collector's own /api/performance/trace uploads are excluded. Answers "was a fetch in flight when the frame died".
  • GC proxy: JS heap sampled once per second inside the window, stored as heap_min_mb/heap_max_mb. A wide span whose end value falls back down is the collector-visible GC sawtooth; there is no direct GC observer on the web platform.
  • Visibility: hidden_ms and visibility_change_count per window. A "stall" that overlaps hidden time is an app switch or screen-off, not jank, and must not be chased as a rendering bug.
  • LoAF invoker: top scripts now carry the LoAF invoker (e.g. FrameRequestCallback, TimerHandler, an event listener name) beside the source URL, because hashed chunk URLs alone under-identify the culprit.
  • Scene composition (draw calls, triangles, meshes, instances, lights, particles, materials, mine canvas diagnostics) was already per-snapshot from the first slice; "too many objects/vertices" hypotheses read straight from those factor columns.

Reliable build id

app_build previously came from git rev-list --count HEAD at request time: null in deployed functions (no git checkout) and a constant 10 on statically built pages (Vercel's shallow clone). next.config.ts now bakes minutes-since-2026-01-01 UTC at build time and getAppRelease prefers it (git count remains the dev fallback). Build ids are monotonic across deploys, so "filter baselines to post-fix builds" and per-build A/B splits work; rows with app_build null or 10 predate the fix.

Query path additions

  • sessions: one rollup per session (prefix, gpu, viewport, DPR, tier, variant, build, totals for stalls, long frames, LoAF, long tasks, hidden time, network; heap range; worst/max frame) with a softwareRenderer flag so SwiftShader/llvmpipe harness sessions label themselves.
  • ?device=real|software: excludes or isolates harness GPUs in every rollup.
  • ?session=<hex prefix>: narrows the window to one session and returns sessionDetail, the per-snapshot expansion with LoAF scripts, network requests, heap span, hidden time, and canvas diagnostics. This is the surface that turns "session 4d2ecd had a 1.4 s frame" into "chunk X burned 900 ms inside a timer while /api/mine took 400 ms".
  • Worst rows carry the same attribution lists inline.

Privacy stance is unchanged from Q-016 default A: aggregates and anonymized columns only, session ids truncated to 6 hex chars, no player ids, no user agents, and network paths can never carry tokens because query strings are stripped at the collector. The expanded collection is disclosed in the toggle copy and the 0.1.198 release note.

Known gap

gpuFrameMs exists only on the WebGPU backend (timestamp queries); the webgl2 path has no equivalent wired (three's WebGLRenderer does not expose the disjoint timer query cleanly). CPU-vs-GPU attribution on webgl2 devices is inferred instead: a steady vsync-locked frame time with LoAF/long-task spikes is CPU-side; a p95 wedged above the vsync interval with quiet main-thread observers points at the GPU.
